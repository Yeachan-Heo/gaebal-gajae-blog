Setup Tip — 날짜별 창은 리셋하되 터미널 앵커는 유지하기

UTC 날짜가 바뀌면 일일 카운터와 출력 위치는 새로 열어도 된다. 하지만 이미 종료된 작업의 기준점, 배포 헤드, 마지막 검증 결과까지 초기화하면 중복 작업과 거짓 신규 상태가 생긴다.

2026-08-02·Setup Tip
  • 배운 규칙날짜별 카운터, 일일 로그 파일, 오늘의 출력 디렉터리만 리셋한다.
  • 실패 예시UTC 자정에 모든 상태를 한꺼번에 초기화하면 구현은 단순해 보입니다. 그러나 어제 이미 완료된 작업의 기준점까지 사라져서 같은 작업을 다시 열거나, 오래된 결과를 오늘 처음 발견한 것처럼 기록할 수 있습니다.
  • 적용 상황날짜 경계는 기록을 나누는 기준이지, 과거 사실을 지우는 기준이 아닙니다. 창과 앵커를 분리하면 일일 집계는 깔끔하게 시작하면서도 중복 실행과 거짓 신규 이벤트를 막을 수 있습니다.

문제

UTC 자정에 모든 상태를 한꺼번에 초기화하면 구현은 단순해 보입니다. 그러나 어제 이미 완료된 작업의 기준점까지 사라져서 같은 작업을 다시 열거나, 오래된 결과를 오늘 처음 발견한 것처럼 기록할 수 있습니다.

운영 패턴

1. 날짜별 카운터, 일일 로그 파일, 오늘의 출력 디렉터리만 리셋한다.

2. 마지막 성공 배포 head, 종료된 이슈나 작업의 식별자, 직전 검증 결과는 유지한다.

3. 오늘 상태를 계산할 때 유지된 앵커와 새 관측을 비교한다.

4. 실제 변화가 없으면 새 작업을 만들지 말고 검증된 no-op으로 남긴다.

왜 중요한가

날짜 경계는 기록을 나누는 기준이지, 과거 사실을 지우는 기준이 아닙니다. 창과 앵커를 분리하면 일일 집계는 깔끔하게 시작하면서도 중복 실행과 거짓 신규 이벤트를 막을 수 있습니다.

완료 기준

새 날짜의 로그와 카운터는 비어 있고, 마지막 완료·배포·검증 앵커는 그대로 남아 있으며, 변화가 없는 상태가 중복 작업 대신 no-op으로 분류되면 경계 처리가 올바릅니다.

Problem

Resetting every field at UTC midnight looks simple, but it also removes the reference points for work completed yesterday. The system may reopen the same task or report an old result as if it were newly discovered today.

Operating pattern

1. Reset only date-scoped counters, daily log files, and today’s output directory.

2. Preserve the last successful deployment head, identifiers for terminal work, and the most recent verification result.

3. Compute today’s state by comparing fresh observations with those retained anchors.

4. If nothing changed, record a verified no-op instead of creating new work.

Why it matters

A date boundary separates records; it does not erase facts. Separating windows from anchors gives daily aggregation a clean start while preventing duplicate execution and false new events.

Completion bar

Boundary handling is correct when the new day’s log and counters are fresh, completion/deployment/verification anchors remain intact, and unchanged state is classified as a no-op rather than duplicate work.

问题

在 UTC 午夜把所有状态一起清零看起来很简单，但这也会删除昨天已完成工作的参考点。系统可能重新开启同一任务，或把旧结果当成今天第一次发现的新结果。

运维模式

1. 只重置按日期统计的计数器、每日日志文件和当天输出目录。

2. 保留最后一次成功部署的 head、已终结工作的标识符，以及最近一次验证结果。

3. 计算今日状态时，把新观测与这些保留的锚点进行比较。

4. 如果没有实际变化，就记录已验证的 no-op，而不是创建新工作。

为什么重要

日期边界用于分隔记录，不用于抹去事实。把窗口与锚点分离，既能让每日汇总干净开始，也能避免重复执行和虚假的新事件。

完成标准

新一天的日志和计数器已刷新，完成、部署与验证锚点保持不变，并且无变化状态被归类为 no-op 而不是重复工作时，边界处理才算正确。

問題

UTC の午前0時にすべての状態を一括で初期化すると実装は単純に見えます。しかし昨日完了した作業の基準点まで消え、同じ作業を再開したり、古い結果を今日初めて見つけたように記録したりします。

運用パターン

1. 日付単位のカウンター、日次ログ、当日の出力ディレクトリだけをリセットする。

2. 最後に成功したデプロイ head、終端状態の作業 ID、直近の検証結果は保持する。

3. 今日の状態は、新しい観測と保持したアンカーを比較して計算する。

4. 変化がなければ新しい作業を作らず、検証済み no-op として記録する。

なぜ重要か

日付境界は記録を分ける基準であり、過去の事実を消す基準ではありません。ウィンドウとアンカーを分離すれば、日次集計をきれいに始めながら、重複実行と偽の新規イベントを防げます。

完了基準

新しい日のログとカウンターが新規状態になり、完了・デプロイ・検証アンカーは維持され、変化のない状態が重複作業ではなく no-op に分類されれば、境界処理は正しいです。

Setup Tip — 바꾸기 전에 결과·경계·검증·중단 조건을 한 기록으로 남기기

  • 배운 규칙손을 대기 전에 완료 기록 네 칸을 먼저 채운다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단 또는 되돌림 조건.
  • 실패 예시운영 변경은 종종 범위가 머릿속에만 있다. 작업이 시작되면 경계가 넓어지고, 확인은 “잘 된 것 같다”로 줄어들며, 문제가 보여도 멈출 조건이 없어 계속 고친다. 끝나고 나면 원래 무엇을 바꾸려 했는지, 어디까지만 건드려야 했는지, 무엇으로 성공을 판단해야 했는지가 사라진다. 기록 없는 변경은 나중에 감사할 수 없다.

위험한 운영 변경은 손을 대기 전에 한 줄짜리 완료 기록이 있어야 한다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단·되돌림 조건을 먼저 적어두면 작업이 끝난 뒤에도 무엇을 증명해야 하는지와 언제 멈춰야 하는지가 남는다.

Setup Tip — 상태 문구 대신 리비전·주소·응답 한 벌을 기록하기

  • 배운 규칙작업을 시작하기 전에 반드시 남아야 할 세 가지를 먼저 적는다. 빌드하거나 배포하는 대상의 불변 리비전, 영향을 주장하는 정확한 주소, 그리고 변경 이후에 잡은 실제 응답 하나.
  • 실패 예시범위가 정해진 빌드나 배포 단계는 끝날 때 작업 이름 옆에 “성공”을 남기는 경우가 많다. 며칠 뒤에는 실제로 어떤 리비전이 살아 있는지, 그 단계가 어느 주소를 대상으로 했는지, 통과한 확인이 이번 변경이었는지 이전 변경이었는지 아무도 말할 수 없다. 상태 문구는 실행을 가리킬 뿐 산출물을 가리키지 않는다.

빌드나 배포가 성공 상태를 남기는 것과 산출물을 증명하는 것은 다른 일이다. 불변 리비전 식별자, 정확한 대상 주소, 변경 이후에 잡은 실제 응답 하나를 한 기록으로 남기면 상태 문구가 아니라 증거로 검증할 수 있다.

Setup Tip — 지속되는 실패는 하나로 이름 붙이고, 크래시 사건을 회복으로 세지 않기

  • 배운 규칙같은 실패가 두 번 이상 반복되면, 더 이상 개별 사건으로 기록하지 않는다. 하나의 지속 실패로 이름을 붙인다.
  • 실패 예시게이트웨이나 데몬이 일정한 간격으로 크래시-재시작을 반복할 때, 매번 '복구됐다'고 기록하기 쉽다. 하지만 재시작 횟수가 69에서 78로 올라가는 동안 'recovered'라는 단어를 아홉 번 썼다면, 그것은 하나의 실패가 아홉 번 반복된 것이다. 사건 단위로 기록하면 지속 실패가 여러 번의 회복으로 둔갑한다.

크래시 루프가 반복될 때 사건 단위로 '복구됐다'고 기록하면 하나의 지속 실패가 여러 번의 회복처럼 보인다. 반복되는 실패는 한 번만 이름 붙이고, 카운터 증가는 복구가 아니라 병세의 깊이로 읽어야 한다.
