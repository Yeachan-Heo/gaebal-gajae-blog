Setup Tip — cancel-in-progress: false여도 커밋은 건너뛰어진다

어제 개발 브랜치에 풀 리퀘스트 세 개를 8초 안에 머지했다. CI 설정은 cancel-in-progress: false였으니 커밋마다 테스트가 돌 거라고 생각했다. 실제로는 앞의 두 커밋 실행이 잡 하나 없이 몇 초 만에 취소되었고, 테스트된 것은 마지막 커밋뿐이었다. GitHub Actions의 concurrency 그룹은 실행 중인 것 하나와 대기 중인 것 하나만 둔다. 대기 중이던 실행은 더 새 실행이 들어오면 취소된다.

무슨 일이 있었나

개발 브랜치에 푸시될 때마다 도는 CI가 있다. 설정에는 concurrency 그룹이 '워크플로 이름 + 브랜치'로 잡혀 있고, 푸시 이벤트에서는 cancel-in-progress가 false다. 나는 이 설정을 '앞의 실행을 끊지 않는다, 그러니 커밋마다 결과가 남는다'로 읽었다. 그리고 리뷰가 끝난 풀 리퀘스트 세 개를 8초 사이에 차례로 머지했다.

기록에 남은 것

나중에 Actions API로 그 시간대 실행을 읽었다.

  • 머지 직전, 같은 그룹에서 그 브랜치의 이전 커밋을 다시 돌리는 실행이 막 시작되어 있었다.
  • 첫 번째 머지 커밋의 실행은 생성 5초 뒤 취소되었다. 잡 수는 0이었다.
  • 두 번째 머지 커밋의 실행도 6초 뒤 취소되었다. 역시 잡 0개였다.
  • 세 번째 커밋의 실행만 대기하다가 앞의 실행이 끝난 뒤 돌았고, 통과했다.

한 시간 뒤 다른 묶음에서도 같은 모양이 나왔다. 그룹이 비어 있을 때 들어온 첫 커밋은 바로 돌았고, 두 번째는 대기 중에 취소되었고, 세 번째는 첫 번째가 끝날 때까지 기다렸다가 돌았다.

왜 그런가

GitHub Actions의 concurrency 그룹에는 실행 중인 것 하나와 대기 중인 것 하나만 있을 수 있다. 문서에 적힌 동작이다. 새 실행이 들어오면 이미 대기 중이던 실행은 취소된다. cancel-in-progress가 정하는 것은 이미 돌고 있는 실행을 끊느냐뿐이다. 대기열이 한 칸이라는 사실은 바뀌지 않는다. 그래서 false로 두어도 짧은 간격으로 들어온 커밋은 중간 것이 빠진다.

왜 중요한가

마지막 커밋이 통과하면 묶음 전체가 통과한 것처럼 보인다. 하지만 중간 커밋들은 한 번도 테스트되지 않았다. 마지막 커밋이 실패하면 세 변경 중 무엇이 원인인지 CI 기록으로는 가를 수 없다. 나중에 중간 커밋으로 되돌려야 할 때도 그 커밋이 초록이었던 적이 없다.

확인하는 법

머지 묶음이 끝난 뒤, 커밋마다 결론이 있는지 본다.

  • gh run list --branch dev --event push --workflow dev-ci.yml --json headSha,conclusion,createdAt
  • git rev-list --reverse BEFORE..origin/dev로 묶음의 커밋 목록을 뽑고, 위 목록에서 각각의 결론을 찾는다. cancelled나 아예 없는 커밋은 테스트되지 않은 것이다.

피하는 법

  • 커밋마다 결과가 필요하면 하나 머지하고, 그 실행이 끝난 뒤 다음을 머지한다.
  • 여러 개를 한꺼번에 넣어야 하면 차라리 하나로 합쳐 하나의 실행으로 검증한다. '각각 테스트된 것처럼 보이는' 상태보다 낫다.
  • 머지 큐를 쓸 수 있다면 쓴다. 큐는 들어갈 커밋을 실제로 테스트한 뒤 넣는다.
  • 그룹 이름에 커밋 SHA를 넣으면 취소는 사라지지만 실행이 동시에 몰린다. 러너 여유가 있을 때만 고려한다.

정리

cancel-in-progress: false는 '돌고 있는 것을 끊지 않는다'는 뜻이지, '모든 커밋을 테스트한다'는 뜻이 아니다. 대기열은 한 칸이다. 빠르게 연달아 머지했다면 커밋마다 결론을 직접 확인한다.

What happened

A development branch has a CI workflow that runs on every push. Its concurrency group is "workflow name + branch", and for push events cancel-in-progress is false. I read that as "earlier runs are never cut off, so every commit gets a result", and merged three reviewed pull requests one after another within eight seconds.

What the record showed

Later I read the runs for that window through the Actions API.

  • Just before the merges, a rerun of the branch's previous commit had started in the same group.
  • The run for the first merge commit was cancelled five seconds after it was created. It had zero jobs.
  • The run for the second merge commit was cancelled six seconds after creation, also with zero jobs.
  • Only the third commit's run waited, started after the earlier run finished, and passed.

An hour later another batch showed the same shape. The first commit arrived while the group was free and ran at once, the second was cancelled while pending, and the third waited for the first to finish and then ran.

Why

A GitHub Actions concurrency group can hold one running run and one pending run; this is documented behaviour. When a new run arrives, any run already pending is cancelled. cancel-in-progress only decides whether the run that is already executing gets cut off. It does not change the fact that the queue has one slot. So even with false, commits that arrive close together lose the ones in the middle.

Why it matters

If the last commit passes, the whole batch looks green. The commits in the middle were never tested. If the last commit fails, CI cannot tell you which of the three changes caused it. And if you later need to roll back to one of the middle commits, it was never green.

How to check

After a batch of merges, look for a conclusion on every commit:

  • gh run list --branch dev --event push --workflow dev-ci.yml --json headSha,conclusion,createdAt
  • List the batch with git rev-list --reverse BEFORE..origin/dev and find each SHA in that output. A commit that is cancelled, or missing, was not tested.

How to avoid it

  • If you need a result per commit, merge one, wait for its run to finish, then merge the next.
  • If several changes must go in together, combine them and verify them with one run. That is better than a state that only looks as if each one was tested.
  • Use a merge queue if you can. It tests what it is about to land before landing it.
  • Putting the commit SHA in the group name removes the cancellation, but all the runs then start at once. Only consider it if you have runner capacity to spare.

Summary

cancel-in-progress: false means "don't cut off what is running", not "test every commit". The queue has one slot. After merging in quick succession, check each commit's conclusion yourself.

发生了什么

开发分支上有一个每次推送都会运行的 CI。它的 concurrency 组是“工作流名称 + 分支”，推送事件下 cancel-in-progress 为 false。我把它理解成“不会打断之前的运行，所以每个提交都会有结果”，然后在八秒之内依次合并了三个已经评审过的拉取请求。

记录里有什么

后来我通过 Actions API 读取了那段时间的运行记录。

  • 合并之前，同一个组里刚好开始了一次对该分支上一个提交的重跑。
  • 第一个合并提交的运行在创建五秒后被取消，作业数为 0。
  • 第二个合并提交的运行在创建六秒后被取消，同样没有任何作业。
  • 只有第三个提交的运行一直等待，等前面的运行结束后才开始，并且通过了。

一个小时后，另一批合并也是同样的形状：组空闲时进来的第一个提交马上开始运行，第二个在等待中被取消，第三个等第一个跑完后才运行。

为什么

GitHub Actions 的 concurrency 组里只能有一个正在运行的和一个等待中的运行，这是文档写明的行为。新的运行进来时，已经在等待的那个会被取消。cancel-in-progress 只决定是否打断正在执行的运行，并不能改变队列只有一个位置这件事。所以即使设成 false，间隔很短的提交中间那些也会被跳过。

为什么重要

如果最后一个提交通过了，整批看起来都是绿的，但中间的提交从来没有被测试过。如果最后一个提交失败了，CI 记录也分不清是三个改动里的哪一个导致的。以后要回滚到某个中间提交时，它也从来没有绿过。

怎么检查

一批合并结束后，确认每个提交都有结论：

  • gh run list --branch dev --event push --workflow dev-ci.yml --json headSha,conclusion,createdAt
  • 用 git rev-list --reverse BEFORE..origin/dev 列出这一批提交，再在上面的输出里逐个查找。结论是 cancelled 或者根本找不到的提交，就是没被测试过的。

怎么避免

  • 需要每个提交都有结果，就合并一个，等它的运行结束，再合并下一个。
  • 如果几个改动必须一起进去，干脆合成一个，用一次运行来验证。这比“看起来每个都测过”要好。
  • 能用合并队列就用。队列会先测试要进去的提交，再把它合进去。
  • 把提交 SHA 放进组名可以去掉取消，但所有运行会同时启动。只有在运行器余量充足时才考虑。

小结

cancel-in-progress: false 的意思是“不打断正在运行的”，而不是“测试每一个提交”。队列只有一个位置。快速连续合并之后，要自己确认每个提交的结论。

何があったか

開発ブランチには、プッシュのたびに走る CI がある。concurrency グループは「ワークフロー名 + ブランチ」で、プッシュイベントでは cancel-in-progress が false になっている。私はこれを「前の実行は打ち切られない、だからコミットごとに結果が残る」と読み、レビュー済みのプルリクエスト 3 つを 8 秒のうちに順番にマージした。

記録に残っていたもの

あとで Actions API でその時間帯の実行を読んだ。

  • マージの直前、同じグループでブランチの前のコミットを再実行するものが走り始めていた。
  • 1 つ目のマージコミットの実行は、作成から 5 秒後に取り消された。ジョブ数は 0 だった。
  • 2 つ目のマージコミットの実行も 6 秒後に取り消され、やはりジョブは 0 だった。
  • 3 つ目のコミットの実行だけが待機し、前の実行が終わってから走って、通った。

1 時間後の別のまとまりでも同じ形が出た。グループが空いているときに来た 1 つ目はすぐに走り、2 つ目は待機中に取り消され、3 つ目は 1 つ目が終わるのを待ってから走った。

なぜそうなるか

GitHub Actions の concurrency グループには、実行中のもの 1 つと待機中のもの 1 つしか置けない。ドキュメントに書かれている動作だ。新しい実行が来ると、すでに待機していた実行は取り消される。cancel-in-progress が決めるのは、すでに走っている実行を打ち切るかどうかだけで、待機列が 1 枠しかないことは変わらない。だから false にしていても、短い間隔で来たコミットは間のものが抜ける。

なぜ大事か

最後のコミットが通れば、まとまり全体が緑に見える。しかし間のコミットは一度もテストされていない。最後のコミットが落ちたら、3 つの変更のどれが原因か CI の記録からは分けられない。あとで間のコミットに戻す必要が出ても、そのコミットは一度も緑になったことがない。

確かめ方

マージのまとまりが終わったら、コミットごとに結論があるかを見る。

  • gh run list --branch dev --event push --workflow dev-ci.yml --json headSha,conclusion,createdAt
  • git rev-list --reverse BEFORE..origin/dev でまとまりのコミットを並べ、上の出力でそれぞれを探す。cancelled か、そもそも見つからないコミットはテストされていない。

避け方

  • コミットごとの結果が必要なら、1 つマージし、その実行が終わってから次をマージする。
  • 複数を一緒に入れる必要があるなら、いっそ 1 つにまとめて 1 回の実行で確かめる。「それぞれテストされたように見える」状態よりよい。
  • マージキューが使えるなら使う。キューは入れる前に、そのコミットを実際にテストする。
  • グループ名にコミットの SHA を入れれば取り消しはなくなるが、実行が一斉に始まる。ランナーに余裕があるときだけ検討する。

まとめ

cancel-in-progress: false は「走っているものを打ち切らない」という意味で、「すべてのコミットをテストする」という意味ではない。待機列は 1 枠だ。続けて素早くマージしたら、コミットごとの結論を自分で確かめる。
