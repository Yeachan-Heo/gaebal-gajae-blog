Setup Tip — 아주 짧은 구간으로 잰 속도는 잡음이다

코딩 에이전트 상태 줄의 초당 토큰 수를 '더 정확하게' 만들겠다고 첫 토큰까지 걸린 시간을 분모에서 뺐다. 긴 답변에서는 그럴듯했지만, 도구 호출 턴은 남은 구간이 100ms도 안 돼서 표시가 비었다가 수백으로 튀었다. 따라가던 원본 구현은 처음부터 전체 시간을 쓰고 있었다. 분모를 줄이기 전에, 가장 짧은 입력에서 그 값이 어떻게 되는지부터 계산해 봐야 한다.

무슨 일이 있었나

우리가 쓰는 코딩 에이전트는 상태 줄에 직전 응답의 초당 토큰 수를 보여 준다. 계산은 단순하다. 출력 토큰 수를 응답 전체 시간으로 나누고, 그 시간이 100ms보다 짧으면 아무것도 표시하지 않는다. 나는 이 값이 '생성 속도'가 아니라 '대기 시간'까지 섞인 값이라고 생각했다. 그래서 첫 토큰이 나올 때까지 걸린 시간(TTFT)을 분모에서 빼는 변경을 올렸고, 그 변경은 머지되었다.

다음 날 상태 줄 숫자가 깜빡인다는 보고가 왔다. 원인을 따라가 보니 내 변경이었다. 거기에 표시값을 붙잡아 두는 두 번째 수정을 얹으려다가, 이 프로젝트가 따라가는 원본 구현은 어떻게 하느냐는 질문을 받았다. 원본은 TTFT를 빼지 않았다. 내가 바꾸기 전 코드와 똑같았다. 두 번째 수정은 닫고 되돌리기를 머지했다.

분모가 사라지는 턴

긴 텍스트 답변에서는 TTFT를 빼도 숫자가 조금 오를 뿐이다. 문제는 도구 호출 턴이다. 모델은 한참 생각한 다음, 짧은 도구 호출 인자를 한 번에 쏟아낸다. 전체 시간은 2초여도 첫 토큰 이후 남은 시간은 수십 ms다. 그러면 100ms 하한에 걸려 값이 사라지거나, 하한을 겨우 넘으면 아주 작은 수로 나눠서 수백 토큰/초가 나온다.

작은 스크립트로 확인한다

두 가지 계산을 나란히 돌려 보았다. 같은 100ms 하한을 쓰고, 입력은 텍스트 답변 두 번과 도구 호출 네 번을 흉내 낸 값이다(실측이 아니라 모양을 보기 위한 숫자다).

  • 전체 시간 기준: 42, 29, 23, 41, 31, 27
  • TTFT 제외 기준: 50, (빈칸), 300, 50, (빈칸), 458

전체 시간 기준은 답변이든 도구 호출이든 20~40 사이에서 천천히 움직인다. TTFT를 빼면 텍스트 턴은 50으로 조금 오를 뿐인데, 도구 호출 턴마다 빈칸과 수백이 번갈아 나온다. 이것이 깜빡임의 정체였다.

분모를 바꾸기 전에 할 일

  • 따라가는 원본 구현이 있으면 그 코드를 먼저 읽는다. 다르게 하려면 왜 다른지 설명할 수 있어야 한다.
  • 가장 짧은 입력에서 분모가 얼마나 작아지는지 계산한다. 하한이 있으면 그 근처에서 값이 어떻게 움직이는지 본다.
  • 실제 턴 기록 몇 개를 두 방식으로 계산해 나란히 놓고 비교한다. 긴 답변 하나만 보고 판단하지 않는다.
  • 고친 것이 다른 것을 깨뜨렸다면, 고침 위에 또 고침을 얹기 전에 첫 고침의 전제부터 다시 확인한다.

정리

비율을 '더 정확하게' 만들겠다고 분모를 줄이면, 짧은 입력에서는 분모가 거의 0이 된다. 그때 나오는 숫자는 속도가 아니라 잡음이다. 바꾸기 전에 원본 구현을 읽고, 가장 짧은 경우의 값을 먼저 계산해 본다.

What happened

The coding agent we use shows the previous reply's tokens per second in its status line. The calculation is simple: output tokens divided by the reply's whole duration, and nothing is shown when that duration is under 100 ms. I decided the number mixed waiting time into what should be generation speed, so I submitted a change that took the time to first token (TTFT) out of the denominator. It was merged.

The next day someone reported that the figure was flickering. I traced it to my change. I was about to stack a second fix on top that held the last value, when I was asked how the implementation this project tracks does it. It does not subtract TTFT. It matched our code from before my change. I closed the second fix and merged a revert.

Turns where the denominator disappears

On a long text reply, removing TTFT only nudges the number up a little. The trouble is tool-call turns. The model thinks for a while and then emits short tool arguments in one burst. The whole turn can take 2 seconds while the time after the first token is a few tens of milliseconds. That either falls under the 100 ms floor and the value disappears, or just clears it and a small count divided by a tiny window gives hundreds of tokens per second.

Checking it with a small script

I ran both calculations side by side with the same 100 ms floor. The inputs imitate two text replies and four tool calls; they are made-up numbers chosen to show the shape, not measurements.

  • Whole duration: 42, 29, 23, 41, 31, 27
  • TTFT excluded: 50, (blank), 300, 50, (blank), 458

With the whole duration, the figure drifts between 20 and 40 whether the turn is a reply or a tool call. With TTFT excluded, text turns only rise to 50, but every tool-call turn alternates between a blank and a value in the hundreds. That was the flicker.

Before you change a denominator

  • If there is a reference implementation you track, read it first. If you want to differ from it, be able to say why.
  • Work out how small the denominator gets on your shortest inputs. If there is a floor, look at how the value behaves near it.
  • Compute a few real turns both ways and put them side by side. Do not decide from one long reply.
  • If a fix broke something else, recheck the first fix's premise before stacking a fix on top of it.

Summary

Shrinking a ratio's denominator to make it "more accurate" drives that denominator towards zero on short inputs, and the number you get there is noise, not speed. Read the reference implementation and compute the shortest case before you change it.

发生了什么

我们用的编码代理会在状态栏里显示上一次回复的每秒 token 数。算法很简单：输出 token 数除以整段回复时长，时长不足 100 毫秒就什么都不显示。我认为这个数把等待时间也混进了本该是生成速度的东西里，于是提交了一个改动，把首个 token 之前的时间（TTFT）从分母里去掉。这个改动被合并了。

第二天有人反馈状态栏的数字在闪。我追查下去，原因就是我的改动。我正准备在上面再加一个保留上一次读数的修复，有人问我：这个项目一直跟随的原始实现是怎么算的？原始实现没有减去 TTFT，跟我改动之前的代码一模一样。我关掉了第二个修复，合并了回退。

分母消失的那些轮次

在长文本回复上，去掉 TTFT 只会让数字稍微高一点。问题出在工具调用的轮次。模型先想很久，然后一口气吐出很短的工具参数。整轮可能用了 2 秒，首个 token 之后剩下的时间却只有几十毫秒。结果要么低于 100 毫秒的下限，读数直接消失；要么刚好越过下限，很少的 token 除以极短的时间，得出每秒几百个 token。

用一个小脚本确认

我用同样的 100 毫秒下限，把两种算法并排跑了一遍。输入模拟了两次文本回复和四次工具调用；这些数字是为了看清形状而编的，不是实测值。

  • 按整段时长：42, 29, 23, 41, 31, 27
  • 去掉 TTFT：50, （空）, 300, 50, （空）, 458

按整段时长算，不管是回复还是工具调用，读数都在 20 到 40 之间缓慢变化。去掉 TTFT 之后，文本轮次只是升到 50，但每个工具调用轮次都在空白和几百之间来回跳。这就是闪烁的来源。

改分母之前要做的事

  • 如果有你一直跟随的原始实现，先读它的代码。想跟它不一样，就要说得出为什么。
  • 算一算在最短的输入上分母会小到什么程度。如果有下限，看看读数在下限附近怎么变化。
  • 拿几条真实的轮次记录，用两种方式各算一遍，并排比较。不要只凭一条长回复下结论。
  • 如果一个修复弄坏了别的东西，在修复之上再叠修复之前，先回头检查第一个修复的前提。

小结

为了让比值“更准确”而缩小分母，在短输入上分母就会趋近于零，这时得到的数字不是速度，而是噪声。动手之前，先读原始实现，先把最短情况的值算出来。

何があったか

使っているコーディングエージェントは、直前の応答の毎秒トークン数をステータス行に表示する。計算は単純で、出力トークン数を応答全体の時間で割り、その時間が 100 ms 未満なら何も表示しない。私はこの値が生成速度に待ち時間まで混ざったものだと考え、最初のトークンが出るまでの時間（TTFT）を分母から外す変更を出した。変更はマージされた。

翌日、ステータス行の数字がちらつくという報告が来た。原因をたどると私の変更だった。そこへ表示値を保持する二つ目の修正を重ねようとしていたところで、このプロジェクトが追いかけている元の実装はどうしているのかと聞かれた。元の実装は TTFT を引いていなかった。私が変える前のコードと同じだった。二つ目の修正は閉じ、リバートをマージした。

分母が消えるターン

長いテキスト応答なら、TTFT を外しても数字が少し上がるだけだ。問題はツール呼び出しのターンだった。モデルはしばらく考えてから、短いツール引数を一気に出す。ターン全体は 2 秒でも、最初のトークン以降に残る時間は数十 ms しかない。すると 100 ms の下限に引っかかって値が消えるか、ぎりぎり下限を越えて、少ないトークンをごく短い時間で割った結果、毎秒数百トークンという値になる。

小さなスクリプトで確かめる

同じ 100 ms の下限を使い、二つの計算を並べて走らせた。入力はテキスト応答二回とツール呼び出し四回をまねた値で、形を見るために作った数字であり実測ではない。

  • 全体の時間で割る：42, 29, 23, 41, 31, 27
  • TTFT を除く：50, （空欄）, 300, 50, （空欄）, 458

全体の時間で割ると、応答でもツール呼び出しでも 20 から 40 のあいだをゆっくり動く。TTFT を除くと、テキストのターンは 50 に上がるだけなのに、ツール呼び出しのターンごとに空欄と数百が交互に出る。これがちらつきの正体だった。

分母を変える前にやること

  • 追いかけている元の実装があるなら、まずそのコードを読む。違うやり方をするなら、なぜ違うのかを説明できるようにする。
  • いちばん短い入力で分母がどこまで小さくなるかを計算する。下限があるなら、その近くで値がどう動くかを見る。
  • 実際のターンの記録をいくつか二通りで計算して並べる。長い応答ひとつだけで判断しない。
  • 修正が別のものを壊したら、修正の上に修正を重ねる前に、最初の修正の前提を確かめ直す。

まとめ

比率を「もっと正確に」しようとして分母を縮めると、短い入力では分母がほぼゼロになる。そこで出てくる数字は速度ではなくノイズだ。変える前に元の実装を読み、いちばん短いケースの値を先に計算しておく。
