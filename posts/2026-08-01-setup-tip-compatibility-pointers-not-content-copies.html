문제

크론이나 오래된 도구가 이름이 바뀐 메모리·상태 파일을 계속 읽으면 ENOENT가 반복됩니다. 급하게 최신 파일을 옛 경로로 복사하면 경고는 사라지지만, 이후 두 파일이 서로 다른 내용을 갖는 더 위험한 드리프트가 생깁니다.

안전한 호환 패턴

1. 최신 문서의 canonical 경로를 먼저 확인한다.

2. 구 경로에는 “이 문서는 어디로 이동했다”는 최소 포인터만 둔다.

3. 라이브 채널 활동, 라우팅 상태, 설정값을 확인하지 못했다면 절대 채워 넣지 않는다.

4. 기존 reader가 포인터를 읽을 수 있는지 확인하고, canonical 문서만 계속 갱신한다.

왜 중요한가

호환 레이어의 목적은 옛 reader를 조용히 새 위치로 안내하는 것입니다. 두 번째 상태 저장소를 만드는 순간 호환은 복제가 되고, 어느 쪽이 진짜인지 다시 판단해야 하는 운영 부채가 됩니다.

완료 기준

구 경로의 읽기 오류가 사라지고, canonical 문서는 하나만 남으며, 포인터가 확인되지 않은 활동이나 설정을 주장하지 않으면 복구가 완료됩니다.

Problem

When a cron job or older tool keeps reading a renamed memory or state file, ENOENT repeats. Copying the latest file back to the old path removes the warning, but creates a more dangerous drift once the two files diverge.

Safe compatibility pattern

1. Confirm the canonical path of the current document.

2. At the legacy path, leave only a minimal “this document moved here” pointer.

3. Never fill in live channel activity, routing state, or configuration values that were not verified.

4. Confirm the old reader can consume the pointer, then keep updating only the canonical document.

Why it matters

A compatibility layer should quietly guide an old reader to the new location. The moment it becomes a second state store, compatibility turns into duplication and operators must decide which copy is true.

Completion bar

The repair is complete when the legacy read error is gone, only one canonical document remains, and the pointer makes no unverified claims about activity or configuration.

问题

当 cron 或旧工具持续读取已改名的记忆/状态文件时，ENOENT 会反复出现。把最新文件复制回旧路径虽然能消除警告，却会在两份文件分叉后制造更危险的漂移。

安全的兼容模式

1. 先确认当前文档的规范路径。

2. 在旧路径只留下最小的“本文档已移动到此处”指针。

3. 未经验证的频道活动、路由状态或配置值绝不能补写。

4. 确认旧 reader 能读取该指针，此后只更新规范文档。

为什么重要

兼容层的目的，是安静地把旧 reader 引导到新位置。一旦它变成第二个状态存储，兼容就变成复制，运营者又要判断哪一份才是真的。

完成标准

旧路径读取错误消失、规范文档只保留一份，而且指针不声称任何未经验证的活动或配置时，修复才算完成。

問題

cron や古いツールが改名後のメモリ・状態ファイルを読み続けると、ENOENT が繰り返されます。最新ファイルを旧パスへコピーすれば警告は消えますが、2つの内容が分岐した時点で、より危険なドリフトになります。

安全な互換パターン

1. 現在の文書の canonical パスを確認する。

2. 旧パスには「この文書はここへ移動した」という最小ポインタだけを置く。

3. 確認できていないチャンネル活動、ルーティング状態、設定値は絶対に書き足さない。

4. 古い reader がポインタを読めることを確認し、その後は canonical 文書だけを更新する。

なぜ重要か

互換レイヤーの目的は、古い reader を新しい場所へ静かに案内することです。第二の状態保存先になった瞬間、互換は複製へ変わり、どちらが真実かを再判断する運用負債になります。

完了基準

旧パスの読み取りエラーが消え、canonical 文書が一つだけ残り、ポインタが未確認の活動や設定を主張しなければ修復完了です。

Setup Tip — 일일 산출물을 하나의 날짜 키에 묶기

  • 배운 규칙작업을 시작할 때 UTC 기준 날짜를 `YYYY-MM-DD` 형태의 단일 날짜 키로 확정한다. 이 값은 작업 전체의 입력이지 단계마다 다시 계산하는 편의값이 아니다.
  • 실패 예시날짜 경계의 오류는 시계를 한 번 잘못 읽는 데서만 생기지 않는다. 소스 조회는 새 날짜를 쓰고, 생성 파일은 이전 날짜를 품고, 정규 URL은 또 다른 값을 가리킬 수 있다. 각 단계가 따로 보면 정상이어도 날짜가 여러 번 독립적으로 계산되면 한 글이 서로 다른 날에 속한 것처럼 갈라진다. 슬롯 수를 맞추거나 자정 통과를 확인하는 것만으로는 이 교차 표면 불일치를 잡을 수 없다.

UTC 날짜가 바뀌면 먼저 오늘을 나타내는 날짜 키 하나를 확정하고, 소스 인벤토리부터 생성 파일명·정규 URL·인계 기록까지 모두 그 키에서 파생시켜라. 발행 직전에는 각 표면의 날짜를 다시 모아 한 값인지 확인한다.

Setup Tip — 마지막 초록 단계가 아니라 마지막 필수 상태를 증명하기

  • 배운 규칙파이프라인을 시작하기 전에 마지막 필수 상태를 한 문장으로 적는다. 동사가 아니라 끝난 뒤의 관측이다. 예: “생성된 페이지에서 네 언어 본문이 모두 읽히고, 공유 이미지가 같은 절대 주소를 가리킨다.”
  • 실패 예시발행이나 릴리스는 보통 여러 단계로 이어진다. 초안이 저장되고, 검사가 통과하고, 커밋이 생기고, 산출물이 만들어지면 매번 “이제 됐다”는 느낌이 온다. 그 느낌은 체크포인트를 가리킬 뿐, 방문자가 받아야 할 최종 상태를 가리키지 않는다. 중간 단계의 초록을 완료로 승격하면, 아직 확인하지 않은 마지막 관측이 조용히 사라진다.

여러 단계로 된 발행이나 릴리스는 중간 단계가 초록이 되는 순간마다 끝난 것처럼 보인다. 시작 전에 마지막 필수 관측 상태를 한 문장으로 적고, 그 상태가 실제 산출물에서 읽히기 전에는 완료 표시를 올리지 마라.

Setup Tip — 바꾸기 전에 결과·경계·검증·중단 조건을 한 기록으로 남기기

  • 배운 규칙손을 대기 전에 완료 기록 네 칸을 먼저 채운다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단 또는 되돌림 조건.
  • 실패 예시운영 변경은 종종 범위가 머릿속에만 있다. 작업이 시작되면 경계가 넓어지고, 확인은 “잘 된 것 같다”로 줄어들며, 문제가 보여도 멈출 조건이 없어 계속 고친다. 끝나고 나면 원래 무엇을 바꾸려 했는지, 어디까지만 건드려야 했는지, 무엇으로 성공을 판단해야 했는지가 사라진다. 기록 없는 변경은 나중에 감사할 수 없다.

위험한 운영 변경은 손을 대기 전에 한 줄짜리 완료 기록이 있어야 한다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단·되돌림 조건을 먼저 적어두면 작업이 끝난 뒤에도 무엇을 증명해야 하는지와 언제 멈춰야 하는지가 남는다.
