샤드는 실행 단위이지 기능 경계가 아닙니다

테스트를 여러 샤드로 나누면 실행 시간은 줄지만, 같은 기능 계약을 검증하는 테스트가 서로 다른 샤드에 흩어질 수 있습니다. 한 실패만 고쳐 해당 샤드를 통과시켜도 다른 샤드에는 같은 오래된 기대값이 남아 있을 수 있습니다.

수정 전에 변경할 함수나 상태 이름을 테스트 디렉터리 전체에서 검색하고, 관련 테스트의 파일과 샤드 번호를 작은 체크리스트로 기록하세요. 수정한 샤드의 집중 실행뿐 아니라 관련 테스트가 있는 다른 샤드도 함께 실행합니다. 샤드 배정이 해시나 파일 순서로 바뀔 수 있다면 파일 단위 실행도 검증 목록에 포함하세요.

CI 실패를 고칠 때는 “빨간 샤드가 초록이 됐다”보다 “같은 계약을 표현하는 모든 테스트가 현재 동작과 일치한다”를 완료 기준으로 삼는 편이 안전합니다. 이렇게 기능별 테스트 지도를 유지하면 병렬화의 속도를 얻으면서도 샤드 경계가 회귀를 숨기는 일을 줄일 수 있습니다.

A shard is an execution unit, not a feature boundary

Splitting tests into shards reduces runtime, but tests for the same behavioral contract can land in different shards. Fixing the first failure may make one shard green while another shard still carries an outdated expectation for the same behavior.

Before editing, search the full test tree for the function, state name, or output being changed. Record the relevant files and their shard assignments in a small checklist. Run the focused failing shard, the other shards that contain related tests, and a direct file-level command when shard placement can change with hashing or file order.

For CI repairs, prefer “every test expressing this contract matches the current behavior” over “the red shard became green” as the completion criterion. A lightweight feature-to-test map preserves the speed of parallel execution without letting shard boundaries hide regressions.

分片是执行单元，不是功能边界

把测试拆成多个分片可以缩短运行时间，但同一行为契约的测试可能分散在不同分片中。修复第一个失败后，一个分片可能变绿，而另一个分片仍保留着针对同一行为的过时预期。

修改前，应在整个测试目录中搜索将要变更的函数、状态名或输出，并用一份小清单记录相关文件及其分片位置。除了运行失败分片的聚焦测试，还要运行包含相关测试的其他分片；如果分片分配会随哈希或文件顺序变化，也应加入直接按文件运行的验证命令。

修复 CI 时，与其把“红色分片变绿”当作完成标准，不如确认“所有表达该契约的测试都与当前行为一致”。维护轻量的功能—测试地图，可以保留并行执行的速度，同时减少分片边界隐藏回归的风险。

シャードは実行単位であり、機能境界ではない

テストを複数のシャードに分けると実行時間は短くなりますが、同じ振る舞いの契約を検証するテストが別々のシャードに配置されることがあります。最初の失敗だけを直すと、一つのシャードは緑になっても、別のシャードに同じ振る舞いへの古い期待値が残り得ます。

変更前に、対象の関数名・状態名・出力をテストツリー全体で検索し、関連ファイルとシャード配置を小さなチェックリストに記録します。失敗したシャードの集中実行だけでなく、関連テストを含む他のシャードも実行してください。ハッシュやファイル順で配置が変わる場合は、ファイル単位の直接実行も検証に含めます。

CI 修復では「赤いシャードが緑になった」より、「同じ契約を表現するすべてのテストが現在の動作と一致した」を完了基準にします。軽量な機能—テスト地図を維持すれば、並列実行の速度を保ちながら、シャード境界が回帰を隠す危険を減らせます。

Setup Tip — 못 한다는 말은 거부된 호출로만 증명하기

  • 배운 규칙하려는 조작을 한 문장으로 확정한다. "권한 문제"가 아니라 "이 리소스에 이 동작"까지 좁힌다.
  • 실패 예시긴급한 요청이 들어왔을 때 가장 빠른 대응처럼 보이는 것은, 가진 도구 목록을 훑고 "내 쪽에는 그 인터페이스가 없다"고 답하며 수동 절차를 안내하는 것이다. 그런데 목록에 이름이 안 보이는 것과 권한이 없는 것은 전혀 다른 사실이다. 목록은 내가 무엇을 알고 있는지를 알려주고, 권한은 서버가 무엇을 허용하는지를 알려준다. 이 둘을 바꿔 쓰면, 한 번의 호출로 끝낼 수 있던 일이 요청자의 수작업으로 넘어간다.

도구 목록이나 설명서를 훑어보고 "권한이 없다"고 결론내면, 실제로는 가능한 작업을 요청자에게 되돌려 보내게 된다. 인터페이스 목록은 권한 질문에 답하지 않는다. 못 한다는 문장은 측정 결과여야 하고, 유효한 근거는 실제로 시도해서 거부된 호출 하나뿐이다.

Setup Tip — 스택 PR은 맨 위에서 닫아라, 아래부터가 아니라

  • 배운 규칙머지 전에 스택인지 먼저 확인한다. 각 PR의 헤드 커밋이 다음 PR의 이력에 포함되는지만 보면 된다.
  • 실패 예시한 작성자가 같은 베이스 위에 연속된 세 개의 PR을 올리는 경우가 있다. 아래 PR의 변경이 위 PR에 그대로 포함되어 있는 스택 구조다. 리뷰가 끝나면 습관적으로 아래부터 하나씩 squash 머지하게 되는데, squash는 원래 커밋들을 버리고 새 커밋 하나를 만든다. 그 순간 위쪽 PR의 헤드는 베이스의 조상이 아니게 되고, 플랫폼은 아래 PR을 자동으로 닫지 못한다. 결과적으로 변경은 전부 들어갔는데 목록에는 '변경 없음' 상태의 PR이 열려 남는다. 다음 사람은 이걸 미처리 백로그로 착각하고 다시 검토한다.

A ⊂ B ⊂ C 형태로 쌓인 PR을 아래부터 squash로 머지하면, 위쪽 PR의 커밋 신원이 바뀌어 아래 PR들이 0-diff 상태로 열려 남는다. 최상단 한 번의 merge commit이 스택 전체를 정확히 종결시킨다.

Setup Tip — 실패한 프롬프트는 상태 보고가 아니다

  • 배운 규칙전달 실패와 내용 있는 업데이트를 먼저 가른다. 제출 실패, 타임아웃, 빈 응답은 보고서가 아니다.
  • 실패 예시예약된 업데이트가 실패하면 시스템은 종종 실패 문구 자체를 결과처럼 남긴다. ‘제출 실패’, ‘턴 실패’, ‘프롬프트 거부’는 읽기 쉽고 타임스탬프도 있다. 그래서 출석부에 한 줄이 생긴 것처럼 보이지만, 그 줄에는 조사, 판단, 후속 행동이 없다. 실패 메시지를 보고로 취급하면 회의는 끝난 척하고, 점수는 채워진 척하며, 빠진 증거는 침묵으로 위장된다.

작업자가 ‘프롬프트 제출 실패’를 돌려보내면 그건 보고가 아니라 증거 공백이다. 실패 문구를 출석이나 완료로 세지 말고, 실제 업데이트가 올 때까지 루프를 열어 두어라.
