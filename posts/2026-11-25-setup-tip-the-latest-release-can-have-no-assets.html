Setup Tip — 최신 릴리스에 파일이 하나도 없을 수 있다

어제 한 CLI 도구의 정식 릴리스가 바이너리 없이 공개되었다. 빌드 단계가 실패했는데도 릴리스는 '최신'으로 올라갔고, 업데이트 명령은 새 버전을 찾은 뒤 다운로드에서 404를 받았다. GitHub의 '최신 릴리스'는 첨부 파일이 있는지 보지 않는다. 내려받는 쪽은 파일 목록을 확인하고, 올리는 쪽은 초안으로 만들어 파일을 다 붙인 뒤에 공개한다.

무슨 일이 있었나

한 오픈소스 CLI 도구의 새 정식 버전이 GitHub 릴리스로 공개되었다. 그런데 릴리스 워크플로는 초반의 검증 단계에서 실패했고, 그 뒤의 바이너리 빌드와 업로드 단계는 모두 건너뛰어졌다. 릴리스는 첨부 파일 0개인 상태로 '최신'이 되었다.

이전 버전을 쓰던 사람이 업데이트 명령을 실행하면 이렇게 되었다.

  • 업데이트 명령이 최신 릴리스를 조회해서 '새 버전이 있다'고 알렸다.
  • 자기 플랫폼용 바이너리를 releases/download/<버전>/<파일 이름>에서 받으려 했다.
  • 그 파일이 없으니 404 Not Found로 실패했다. 모든 플랫폼, 모든 사용자가 같았다.

같은 버전을 다시 만들어 파일 10개가 붙은 릴리스로 공개하기까지 약 4시간 반 동안 이 상태였다.

왜 이렇게 되나

GitHub API의 releases/latest는 초안도 프리릴리스도 아닌 가장 최근의 릴리스를 돌려준다. 첨부 파일이 있는지는 기준에 없다. 파일이 0개인 릴리스도 똑같이 '최신'이다.

https://github.com/OWNER/REPO/releases/latest/download/<파일 이름> 형태의 고정 링크도 마찬가지다. 그 시점의 최신 릴리스에서 파일을 찾고, 없으면 404를 돌려준다. 이번 글을 쓰면서 실제로 확인했다. 지금 최신 릴리스에 있는 파일 이름은 200, 없는 이름은 404였다.

즉 '새 버전이 나왔다'와 '새 버전을 받을 수 있다'는 서로 다른 사실이다.

확인하는 법

  • 최신 릴리스의 태그와 파일 개수: gh api repos/OWNER/REPO/releases/latest --jq '.tag_name, (.assets | length)'
  • 파일 이름 목록: gh api repos/OWNER/REPO/releases/latest --jq '.assets[].name'. 릴리스마다 있어야 할 파일 목록과 비교한다.

내려받는 쪽(업데이트 명령, 설치 스크립트)

'최신'을 그대로 믿지 말고, 필요한 파일이 실제로 붙어 있는 가장 최근 정식 릴리스를 고른다.

  • gh api 'repos/OWNER/REPO/releases?per_page=20' --jq '[.[] | select(.draft | not) | select(.prerelease | not) | select(any(.assets[]; .name == "mytool-linux-x64"))][0].tag_name'
  • 결과가 현재 버전과 같거나 비어 있으면 업데이트하지 않는다. 최신 릴리스를 건너뛰었다면 '이 릴리스에는 아직 이 플랫폼용 파일이 없다'고 이유를 알려 준다.

실제로 그 도구의 수정도 이렇게 바뀌었다. 파일이 없는 릴리스는 건너뛰고, 파일이 있는 더 오래된 릴리스로 돌아간다.

올리는 쪽(릴리스 워크플로)

  • 릴리스는 초안으로 만든다: gh release create v1.2.3 --draft. 초안은 releases/latest에 잡히지 않는다.
  • 바이너리를 올린다: gh release upload v1.2.3 dist/*.
  • 파일 목록을 기대 목록과 대조한다. 하나라도 없으면 공개하지 않는다.
  • 그다음에 공개한다: gh api -X PATCH repos/OWNER/REPO/releases/RELEASE_ID -F draft=false. 최근 gh에는 gh release edit v1.2.3 --draft=false도 있다.
  • 워크플로에서 공개 단계는 빌드와 업로드 잡에 의존하게(needs:) 만든다. 앞 단계가 실패하거나 건너뛰어지면 공개 단계도 돌지 않는다.

정리

'최신 릴리스'는 최근에 공개되었다는 뜻일 뿐, 받을 파일이 있다는 뜻이 아니다. 받는 쪽은 파일 목록을 보고 고르고, 올리는 쪽은 파일을 다 붙인 다음에만 초안을 공개로 바꾼다.

What happened

A new stable version of an open-source CLI tool was published as a GitHub release. But the release workflow had failed at an early validation step, and every later step, including building and uploading the binaries, was skipped. The release became "latest" with zero assets attached.

For anyone on the previous version, running the update command went like this:

  • The update command looked up the latest release and reported that a new version was available.
  • It tried to download the binary for its platform from releases/download/<version>/<asset name>.
  • The file did not exist, so the download failed with 404 Not Found. Every platform, every user.

It stayed that way for about four and a half hours, until the same version was rebuilt and published again with ten assets attached.

Why it happens

The GitHub API's releases/latest returns the most recent release that is neither a draft nor a prerelease. Whether it has any assets is not part of that rule. A release with zero files is just as "latest" as any other.

The same goes for the fixed link https://github.com/OWNER/REPO/releases/latest/download/<asset name>. It looks for the file on whatever release is latest at that moment and returns 404 if it is not there. I checked this while writing: an asset name that exists on the current latest release returned 200, and a name that does not exist returned 404.

So "a new version is out" and "the new version can be downloaded" are separate facts.

How to check

  • Tag and asset count of the latest release: gh api repos/OWNER/REPO/releases/latest --jq '.tag_name, (.assets | length)'
  • Asset names: gh api repos/OWNER/REPO/releases/latest --jq '.assets[].name'. Compare against the list of files every release is supposed to carry.

On the download side (update commands, install scripts)

Don't take "latest" at face value. Pick the newest stable release that actually has the file you need:

  • gh api 'repos/OWNER/REPO/releases?per_page=20' --jq '[.[] | select(.draft | not) | select(.prerelease | not) | select(any(.assets[]; .name == "mytool-linux-x64"))][0].tag_name'
  • If the result equals the current version or is empty, don't update. If you skipped the latest release, say why: "this release has no file for this platform yet".

That is how the tool's own fix ended up working: it skips releases without the asset and falls back to an older release that has it.

On the publishing side (the release workflow)

  • Create the release as a draft: gh release create v1.2.3 --draft. Drafts are not returned by releases/latest.
  • Upload the binaries: gh release upload v1.2.3 dist/*.
  • Check the asset list against the expected list. If anything is missing, do not publish.
  • Then publish: gh api -X PATCH repos/OWNER/REPO/releases/RELEASE_ID -F draft=false. Newer versions of gh also have gh release edit v1.2.3 --draft=false.
  • In the workflow, make the publish step depend on the build and upload jobs (needs:). If an earlier step fails or is skipped, the publish step does not run either.

Summary

"Latest release" only means it was published most recently, not that there is anything to download. Downloaders choose by the asset list; publishers turn a draft public only after every file is attached.

发生了什么

一个开源 CLI 工具的新正式版本作为 GitHub release 发布了。可是发布工作流在早期的校验步骤就失败了，之后构建和上传二进制文件的步骤全部被跳过。这个版本在附带文件为 0 的状态下成了“最新版本”。

对还在用上一个版本的人来说，运行更新命令会是这样：

  • 更新命令查询最新版本，提示“有新版本”。
  • 它尝试从 releases/download/<版本>/<文件名> 下载自己平台的二进制文件。
  • 文件不存在，于是以 404 Not Found 失败。所有平台、所有用户都一样。

这个状态持续了大约四个半小时，直到同一个版本重新构建，并带着 10 个文件再次发布。

为什么会这样

GitHub API 的 releases/latest 返回的是既不是草稿、也不是预发布的最近一个版本。有没有附带文件不在判断条件里。0 个文件的版本同样是“最新”。

https://github.com/OWNER/REPO/releases/latest/download/<文件名> 这种固定链接也一样。它会到当时的最新版本里找文件，找不到就返回 404。写这篇时我实际验证过：当前最新版本里存在的文件名返回 200，不存在的文件名返回 404。

也就是说，“新版本出了”和“新版本能下载”是两件不同的事。

怎么检查

  • 最新版本的标签和文件数量：gh api repos/OWNER/REPO/releases/latest --jq '.tag_name, (.assets | length)'
  • 文件名列表：gh api repos/OWNER/REPO/releases/latest --jq '.assets[].name'。与每个版本应该带有的文件列表对比。

下载的一方（更新命令、安装脚本）

不要直接相信“最新”，而是选择真正带有所需文件的最近一个正式版本：

  • gh api 'repos/OWNER/REPO/releases?per_page=20' --jq '[.[] | select(.draft | not) | select(.prerelease | not) | select(any(.assets[]; .name == "mytool-linux-x64"))][0].tag_name'
  • 如果结果与当前版本相同或为空，就不更新。如果跳过了最新版本，要说明原因：“这个版本还没有本平台的文件”。

那个工具后来的修复正是这样做的：跳过没有文件的版本，退回到有文件的更早版本。

发布的一方（发布工作流）

  • 先把版本建成草稿：gh release create v1.2.3 --draft。草稿不会被 releases/latest 返回。
  • 上传二进制文件：gh release upload v1.2.3 dist/*。
  • 把文件列表与预期列表对照。缺任何一个都不公开。
  • 然后再公开：gh api -X PATCH repos/OWNER/REPO/releases/RELEASE_ID -F draft=false。较新版本的 gh 也可以用 gh release edit v1.2.3 --draft=false。
  • 在工作流里，让公开步骤依赖构建和上传作业（needs:）。前面的步骤失败或被跳过，公开步骤也不会运行。

总结

“最新版本”只表示它最近发布，不表示有东西可下载。下载的一方按文件列表来选，发布的一方只在所有文件都附上之后才把草稿改为公开。

何があったか

あるオープンソース CLI ツールの新しい正式バージョンが GitHub のリリースとして公開された。ところがリリースのワークフローは序盤の検証ステップで失敗しており、その後のバイナリのビルドとアップロードはすべてスキップされていた。リリースは添付ファイル 0 個のまま「最新」になった。

前のバージョンを使っていた人がアップデートコマンドを実行すると、こうなった。

  • アップデートコマンドが最新リリースを調べ、「新しいバージョンがある」と知らせた。
  • 自分のプラットフォーム用のバイナリを releases/download/<バージョン>/<ファイル名> から取得しようとした。
  • そのファイルがないので 404 Not Found で失敗した。すべてのプラットフォーム、すべての利用者で同じだった。

同じバージョンを作り直し、ファイル 10 個を添付したリリースとして公開し直すまで、約 4 時間半この状態が続いた。

なぜこうなるか

GitHub API の releases/latest は、下書きでもプレリリースでもない、いちばん新しいリリースを返す。ファイルが添付されているかどうかは条件に入っていない。ファイル 0 個のリリースも、同じように「最新」だ。

https://github.com/OWNER/REPO/releases/latest/download/<ファイル名> という固定リンクも同じだ。その時点の最新リリースからファイルを探し、なければ 404 を返す。この記事を書きながら実際に確かめた。いまの最新リリースにあるファイル名は 200、存在しない名前は 404 だった。

つまり「新しいバージョンが出た」と「新しいバージョンをダウンロードできる」は別の事実だ。

確かめ方

  • 最新リリースのタグとファイル数: gh api repos/OWNER/REPO/releases/latest --jq '.tag_name, (.assets | length)'
  • ファイル名の一覧: gh api repos/OWNER/REPO/releases/latest --jq '.assets[].name'。リリースごとにあるべきファイルの一覧と比べる。

ダウンロードする側（アップデートコマンド、インストールスクリプト）

「最新」をそのまま信じず、必要なファイルが実際に添付されている、いちばん新しい正式リリースを選ぶ。

  • gh api 'repos/OWNER/REPO/releases?per_page=20' --jq '[.[] | select(.draft | not) | select(.prerelease | not) | select(any(.assets[]; .name == "mytool-linux-x64"))][0].tag_name'
  • 結果がいまのバージョンと同じか空なら、アップデートしない。最新リリースを飛ばしたときは「このリリースにはまだこのプラットフォーム用のファイルがない」と理由を伝える。

そのツールの修正も、実際にこうなった。ファイルのないリリースは飛ばし、ファイルのある古いリリースに戻る。

公開する側（リリースのワークフロー）

  • リリースは下書きとして作る: gh release create v1.2.3 --draft。下書きは releases/latest に返されない。
  • バイナリをアップロードする: gh release upload v1.2.3 dist/*。
  • ファイル一覧を期待する一覧と照らし合わせる。1 つでも欠けていれば公開しない。
  • それから公開する: gh api -X PATCH repos/OWNER/REPO/releases/RELEASE_ID -F draft=false。新しい gh なら gh release edit v1.2.3 --draft=false も使える。
  • ワークフローでは、公開ステップをビルドとアップロードのジョブに依存させる（needs:）。前のステップが失敗したりスキップされたりすれば、公開ステップも走らない。

まとめ

「最新リリース」は、いちばん最近公開されたという意味でしかなく、ダウンロードできるものがあるという意味ではない。ダウンロードする側はファイル一覧を見て選び、公開する側はすべてのファイルを添付してから下書きを公開に切り替える。
