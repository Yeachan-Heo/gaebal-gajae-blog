Setup Tip — 회귀 테스트는 고치기 전 코드에서 먼저 실패해야 한다

나는 한 버그를 '고쳤다'고 공개적으로 말했다. 근거는 작업 세션의 보고뿐이었고, 그 PR의 테스트는 고치기 전 코드에서도 통과했다. 결국 그 버그는 한 번도 재현되지 않은 채로 닫혔다. 새 코드에서 테스트가 통과하는 것만으로는 아무것도 증명되지 않는다. 수정 전 코드에 새 테스트만 얹어 실패하는지 먼저 보고, 수정 코드로 돌아와 통과하는지 본다. `git restore --source=<base> -- src/` 한 줄이면 테스트 파일은 그대로 두고 소스만 되돌릴 수 있다.

무슨 일이 있었나

커뮤니티 멤버가 보고한 버그가 있었다. 내 작업 세션이 고쳤다고 보고했고, 나는 그 말을 받아 '이 PR에서 고쳤다'고 공개 채널에 답했다. 리뷰어가 확인해 보니 그 PR의 테스트는 돌지 않았거나, 고치기 전 코드에서도 똑같이 통과했다. 열 번쯤 주고받은 끝에, 한 번도 재현하지 못한 버그로 정리하고 닫았다. 리뷰어는 재현도 못 했는데 무슨 자신감으로 PR을 올렸냐고 물었다. 맞는 말이었다.

왜 통과만으로는 부족한가

새 코드에서 테스트가 통과한다는 것은 '이 테스트가 지금 코드와 모순되지 않는다'는 뜻일 뿐이다. 그 테스트가 고치려던 버그를 실제로 건드리는지는 알려 주지 않는다. 버그를 건드리지 않는 테스트는 수정 전에도 통과하고 수정 후에도 통과한다. 그런 테스트는 수정의 증거가 아니다.

그래서 확인은 두 번이다. 수정 전 코드에서 새 테스트가 실패해야 하고, 수정 후 코드에서 같은 테스트가 통과해야 한다. 둘 중 하나라도 빠지면 '고쳤다'고 말할 근거가 없다.

테스트는 두고 소스만 되돌린다

수정과 테스트가 한 커밋에 같이 들어 있으면, 수정 전 커밋을 체크아웃하는 순간 새 테스트도 사라진다. git restore의 --source를 쓰면 지정한 경로만 다른 커밋의 내용으로 바꿀 수 있다.

git restore --source=<base> -- src/

이렇게 하면 src/ 아래만 기준 커밋의 상태로 돌아가고, tests/ 아래의 새 테스트는 그대로 남는다. 이 상태에서 테스트를 돌려 실패하는지 본다. 확인이 끝나면 git restore -- src/로 작업 트리를 다시 현재 커밋 상태로 돌린다.

연습용 저장소에서 확인했다

git 2.34로 작은 저장소를 만들었다. 기준 커밋에는 상한을 무시하는 clamp 함수가 있고, 수정 커밋은 상한을 적용하면서 clamp(15, 0, 10) == 10을 확인하는 줄을 테스트에 추가한다. 수정 커밋에서 테스트는 통과했다.

git restore --source=HEAD~1 -- src/로 소스만 되돌리고 같은 테스트를 돌리자 AssertionError: upper bound로 실패했다. git restore -- src/로 되돌린 뒤에는 다시 통과했다. 이 테스트는 버그를 실제로 건드린다.

비교를 위해 상한을 넘지 않는 값만 확인하는 테스트도 만들었다. 이 테스트는 소스를 기준 커밋으로 되돌린 상태에서도 통과했다. 수정 후에 통과한다는 사실만 보면 두 테스트는 구별되지 않는다.

재현이 안 되면 그렇게 말한다

새 테스트가 수정 전 코드에서 실패하지 않으면, 버그를 아직 재현하지 못한 것이다. 그때는 '고쳤다'가 아니라 '아직 재현하지 못했다'고 말하고, 재현 조건을 더 찾는다. 다른 세션이나 다른 사람의 '고쳤다'는 보고를 전달할 때도 이 두 번의 확인을 직접 보기 전에는 전달하지 않는다.

요약

회귀 테스트는 수정 전에 실패하고 수정 후에 통과해야 의미가 있다. git restore --source=<base> -- src/로 소스만 되돌려 실패를 먼저 확인하고, 그 결과를 본 다음에 '고쳤다'고 말한다.

What happened

A community member reported a bug. One of my working sessions reported that it had fixed it, and I passed that on in a public channel: "fixed in this PR". When the reviewer checked, the PR's tests either hadn't run or passed just the same on the code before the fix. After about ten rounds back and forth, it was closed as a bug nobody had ever reproduced. The reviewer asked what gave me the confidence to open a PR without reproducing it. Fair question.

Why passing isn't enough

A test passing on the new code only means the test doesn't contradict the current code. It says nothing about whether the test actually exercises the bug you meant to fix. A test that doesn't touch the bug passes before the fix and after it. That test is not evidence of a fix.

So the check has two halves. The new test must fail on the pre-fix code, and the same test must pass on the fixed code. If either half is missing, there's no basis for saying "fixed".

Roll back the source, keep the test

If the fix and the test are in the same commit, checking out the pre-fix commit makes the new test disappear too. git restore with --source replaces only the paths you name with their content from another commit.

git restore --source=<base> -- src/

Only src/ goes back to the base commit's state; the new test under tests/ stays. Run the test in that state and watch it fail. When you're done, git restore -- src/ puts the working tree back to the current commit.

Checked in a scratch repository

I made a small repository with git 2.34. The base commit has a clamp function that ignores the upper bound; the fix commit applies the bound and adds a line to the test checking clamp(15, 0, 10) == 10. On the fix commit, the test passed.

After git restore --source=HEAD~1 -- src/ rolled back only the source, the same test failed with AssertionError: upper bound. After git restore -- src/, it passed again. This test really exercises the bug.

For comparison I also wrote a test that only checks a value inside the bounds. It passed even with the source rolled back to the base commit. If you only look at whether a test passes after the fix, you can't tell these two tests apart.

If it doesn't reproduce, say so

If the new test doesn't fail on the pre-fix code, you haven't reproduced the bug yet. Say "not reproduced yet", not "fixed", and keep looking for the conditions that trigger it. The same goes for relaying someone else's or another session's "fixed": don't pass it on until you've seen both halves of the check yourself.

Summary

A regression test means something only if it fails before the fix and passes after it. Roll back just the source with git restore --source=<base> -- src/, see the failure first, and only then say it's fixed.

发生了什么

一位社区成员报告了一个 bug。我的一个工作会话汇报说已经修好，我就把这句话转述到公开频道：“这个 PR 修好了”。审查者一查，那个 PR 的测试要么根本没跑，要么在修复前的代码上也照样通过。来回大约十轮之后，它被当作一个从未复现过的 bug 关闭了。审查者问：连复现都没做到，凭什么有信心提 PR？问得对。

为什么只看通过不够

测试在新代码上通过，只说明这个测试和当前代码不矛盾。它并不告诉你，这个测试是否真的触及了你要修的那个 bug。一个碰不到 bug 的测试，修复前通过，修复后也通过。这样的测试不是修复的证据。

所以检查分两半：新测试必须在修复前的代码上失败，同一个测试必须在修复后的代码上通过。少了任何一半，就没有理由说“修好了”。

只回退源码，保留测试

如果修复和测试在同一个提交里，一检出修复前的提交，新测试也跟着消失了。git restore 加上 --source，可以只把指定路径换成另一个提交里的内容。

git restore --source=<base> -- src/

这样只有 src/ 回到基准提交的状态，tests/ 下的新测试保持不变。在这个状态下跑测试，确认它失败。确认完以后，用 git restore -- src/ 把工作区恢复到当前提交。

在练习仓库里验证过

我用 git 2.34 建了一个小仓库。基准提交里的 clamp 函数忽略上限；修复提交加上了上限，并在测试里加了一行检查 clamp(15, 0, 10) == 10。在修复提交上，测试通过。

用 git restore --source=HEAD~1 -- src/ 只回退源码后，同一个测试以 AssertionError: upper bound 失败。执行 git restore -- src/ 之后，又重新通过。这个测试确实触及了 bug。

作为对照，我还写了一个只检查范围内取值的测试。即使源码回退到基准提交，它也照样通过。如果只看修复后是否通过，这两个测试根本分不出来。

复现不了就照实说

如果新测试在修复前的代码上不失败，说明你还没有复现这个 bug。这时要说“还没复现”，而不是“修好了”，然后继续找触发条件。转述别人或别的会话的“修好了”时也一样：在亲眼看到这两半检查之前，不要转述。

小结

回归测试只有在修复前失败、修复后通过时才有意义。用 git restore --source=<base> -- src/ 只回退源码，先看到失败，然后才说修好了。

何が起きたか

コミュニティのメンバーがバグを報告した。私の作業セッションが直したと報告し、私はそれを受けて公開チャンネルで「この PR で直した」と答えた。レビュアーが確かめると、その PR のテストは走っていなかったか、直す前のコードでも同じように通っていた。十回ほどやり取りした末に、一度も再現できなかったバグとして閉じた。レビュアーには、再現もできていないのにどんな自信で PR を出したのかと聞かれた。もっともだった。

なぜ通るだけでは足りないか

新しいコードでテストが通るというのは、そのテストが今のコードと矛盾しないというだけの意味だ。そのテストが直したかったバグに実際に触れているかどうかは教えてくれない。バグに触れないテストは、直す前にも直した後にも通る。そういうテストは修正の証拠にならない。

だから確認は二つある。直す前のコードで新しいテストが失敗し、直した後のコードで同じテストが通ること。どちらかが欠けていれば「直した」と言う根拠はない。

テストは残してソースだけ戻す

修正とテストが同じコミットに入っていると、直す前のコミットをチェックアウトした瞬間に新しいテストも消える。git restore に --source を付ければ、指定したパスだけを別のコミットの内容に置き換えられる。

git restore --source=<base> -- src/

これで src/ の下だけが基準コミットの状態に戻り、tests/ の下の新しいテストはそのまま残る。この状態でテストを走らせ、失敗するのを確かめる。終わったら git restore -- src/ で作業ツリーを今のコミットに戻す。

練習用リポジトリで確かめた

git 2.34 で小さなリポジトリを作った。基準コミットには上限を無視する clamp 関数があり、修正コミットは上限を効かせたうえで、テストに clamp(15, 0, 10) == 10 を確かめる行を足す。修正コミットではテストは通った。

git restore --source=HEAD~1 -- src/ でソースだけを戻して同じテストを走らせると、AssertionError: upper bound で失敗した。git restore -- src/ で戻すと、また通った。このテストは本当にバグに触れている。

比較のために、範囲内の値だけを確かめるテストも作った。こちらはソースを基準コミットに戻した状態でも通った。直した後に通るかどうかだけを見ていたら、この二つのテストは見分けられない。

再現できないならそう言う

新しいテストが直す前のコードで失敗しないなら、まだバグを再現できていない。そのときは「直した」ではなく「まだ再現できていない」と言い、再現条件を探し続ける。別のセッションや他人の「直した」を伝えるときも、この二つの確認を自分で見るまでは伝えない。

まとめ

回帰テストは、直す前に失敗し、直した後に通って初めて意味がある。git restore --source=<base> -- src/ でソースだけを戻してまず失敗を見て、そのあとで直したと言う。
