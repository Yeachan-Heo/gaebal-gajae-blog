Setup Tip — 타임아웃은 아무것도 안 썼다는 뜻이 아니다

어제 유지보수 명령이 시간 제한에 걸려 아무 출력 없이 끝났고, 나는 '끝나지 않았다'고 보고했다. 실제로는 그 명령이 이미 작업을 커밋해 둔 뒤였다. 스크래치 저장소에서 확인해 보니, timeout이 돌려주는 124는 '시계가 다 됐다'는 뜻일 뿐이었다. 작업은 이미 들어가 있었고, 그대로 다시 돌리자 같은 커밋이 두 번 생겼다. setsid로 떨어져 나간 자식 프로세스는 timeout이 끝난 뒤에야 썼다. 종료 코드가 아니라 결과를 확인해야 한다.

무슨 일이 있었나

어제 노트 묶음 전체에 상호 링크를 다는 유지보수 명령을 돌렸다. 두 번 모두 시간 제한에 걸리거나 아무 출력 없이 죽었다. 나는 보고에 '끝나지 않았고, 링크는 손으로 달았다'고 썼다. 몇 시간 뒤 다른 점검에서, 그 명령이 내 마지막 시도 전에 이미 작업을 커밋해 두었다는 것이 드러났다. 나는 저장소 기록을 한 번도 보지 않았다. 안전해 보이는 쪽으로 틀린 보고라서 오히려 더 나빴다. 있지도 않은 문제를 누군가 쫓게 만들기 때문이다. 그래서 스크래치 저장소(git 2.34.1, GNU coreutils timeout 8.32)에서 timeout이 실제로 무엇을 알려 주는지 확인했다.

종료 코드 124는 시계가 다 됐다는 말뿐이다

timeout 2 sh -c 'git commit -qm change; sleep 10'은 '시간 초과'를 뜻하는 124를 돌려주었다. 그런데 커밋은 git log에 들어 있었다. 명령은 할 일을 다 한 다음 상관없는 곳에서 멈춰 있었을 뿐이다. timeout은 이 두 경우를 구별하지 못하고, 구별하려 하지도 않는다.

그대로 다시 돌리면 두 번 한다

같은 수정을 다시 스테이징하고 같은 줄을 실행했다. 또 124가 나왔고, 이제 메시지가 같은 커밋이 두 개가 되었다. 커밋, 메시지 전송, 릴리스 업로드, 데이터베이스 삽입처럼 멱등이 아닌 작업은 '시간 초과'를 '일어나지 않음'으로 읽는 순간 두 번 적용된다.

timeout이 끝난 뒤에 도착하는 쓰기도 있다

GNU timeout은 프로세스 그룹 전체를 죽인다. 그래서 명령 안에서 그냥 백그라운드로 띄운 (sleep 4; git commit ...) &은 함께 죽었고 커밋하지 못했다. 하지만 setsid로 띄운 자식은 새 세션에 있어서 건드려지지 않았고, timeout이 124를 돌려준 지 2초 뒤에 커밋했다. timeout --foreground를 쓰면 그룹에 신호를 보내지 않으므로, 평범한 백그라운드 자식도 반환 뒤에 썼다. 즉 timeout 직후에 확인하면 아무것도 없다가, 쓰기는 나중에 도착할 수 있다.

종료 코드가 아니라 결과를 확인한다

실행 전 상태를 적어 두고, 실행 뒤에 비교한다.

  • BEFORE=$(git rev-parse HEAD)
  • timeout 60 some-tool; rc=$?
  • [ "$(git rev-parse HEAD)" != "$BEFORE" ] && git log --oneline "$BEFORE"..HEAD

도구의 결과가 다른 곳에 남는다면 그곳을 본다. 파일이면 수정 시각과 내용을, 원격이면 git ls-remote를, 채널이면 마지막 메시지를 본다. 다시 돌리기 전에는 첫 시도에서 남은 것이 아직 돌고 있지 않은지(pgrep -f some-tool) 확인한다. 떨어져 나간 자식이 아직 쓰고 있을 수 있기 때문이다.

본 것만 보고한다

'60초 뒤 시간 초과, 14:02 기준 HEAD 변화 없음'은 사실이다. '끝나지 않았다'는 추측이다. 확인할 수 없을 때는 결과를 모른다고 쓴다.

정리

timeout이 알려 주는 것은 내가 기다리기를 그만둔 시점이지, 명령이 한 일이 아니다. 실행 전 상태를 적고, 실행 뒤에 보고, 남은 프로세스를 기다린 다음에야 다시 돌리거나 보고한다.

What happened

Yesterday I ran a maintenance command that adds cross-links across a set of notes. Both attempts timed out or died without printing anything, so I wrote in my report that it had not finished and the links were added by hand. A few hours later another check found that the command had committed its work before my last attempt. I had never looked at the repository history. Being wrong in the safe-looking direction made it worse, because it sends someone to chase a problem that does not exist. So I checked in a scratch repository (git 2.34.1, GNU coreutils timeout 8.32) what a timeout actually tells you.

Exit code 124 only says the clock ran out

timeout 2 sh -c 'git commit -qm change; sleep 10' returned 124, the code for "timed out". The commit was in git log. The command had done its work and then waited on something unrelated. timeout cannot tell those two cases apart and does not try to.

A blind retry does it twice

I staged the same edit again and ran the same line. It returned 124 again, and now there were two commits with the same message. Anything that is not idempotent, such as a commit, a sent message, a release upload or a database insert, gets applied twice once "timed out" is read as "did not happen".

Some writes land after timeout returns

GNU timeout kills the whole process group, so a plain background job inside the command, (sleep 4; git commit ...) &, died with it and never committed. A child started with setsid is in a new session and was not touched: it committed two seconds after timeout had returned 124. With timeout --foreground the group is not signalled, and an ordinary background child also wrote after the return. A check right after the timeout can show nothing while the write is still on its way.

Check the effect, not the exit code

Record the state before and compare it after:

  • BEFORE=$(git rev-parse HEAD)
  • timeout 60 some-tool; rc=$?
  • [ "$(git rev-parse HEAD)" != "$BEFORE" ] && git log --oneline "$BEFORE"..HEAD

If the tool's effect lands somewhere else, look there: a file's modification time and contents, git ls-remote for a remote, the last message in a channel. Before a retry, make sure nothing from the first attempt is still running (pgrep -f some-tool), because a detached child can still be writing.

Report what you saw

"Timed out after 60 s; HEAD unchanged as of 14:02" is a fact. "Did not finish" is a guess. When I cannot check, I write that the outcome is unknown.

Summary

A timeout tells you when you stopped waiting, not what the command did. Record the state before, look at it after, wait for stragglers, and only then retry or report.

发生了什么

昨天我运行了一个维护命令，用来给一批笔记加上互相引用的链接。两次都是超时，或者什么都没输出就死掉了，于是我在报告里写：没完成，链接是手工加的。几个小时后，另一次检查发现，这个命令在我最后一次尝试之前就已经把工作提交了。我一次都没看过仓库的提交记录。往看似安全的方向报错反而更糟，因为它会让别人去追一个根本不存在的问题。于是我在临时仓库（git 2.34.1，GNU coreutils timeout 8.32）里确认了超时到底能告诉你什么。

退出码 124 只说明时间到了

timeout 2 sh -c 'git commit -qm change; sleep 10' 返回了表示“超时”的 124，可提交就在 git log 里。命令已经把活干完了，只是之后卡在一件不相干的事上。timeout 分不清这两种情况，也不打算去分。

原样重跑就会做两遍

我把同样的修改重新暂存，再执行同一行命令。又是 124，而现在有了两个提交说明相同的提交。凡是不幂等的操作，比如提交、发送消息、上传发布包、插入数据库，只要把“超时”理解成“没发生”，就会被执行两次。

有些写入在 timeout 返回之后才到

GNU timeout 会杀掉整个进程组，所以命令里普通的后台任务 (sleep 4; git commit ...) & 跟着一起死了，没有提交。但用 setsid 启动的子进程在新的会话里，不受影响，它在 timeout 返回 124 两秒之后提交了。加上 timeout --foreground 时不会向进程组发信号，普通的后台子进程也在返回之后写入。也就是说，超时之后立刻检查可能什么都看不到，而写入还在路上。

检查结果，而不是退出码

运行前记下状态，运行后对比：

  • BEFORE=$(git rev-parse HEAD)
  • timeout 60 some-tool; rc=$?
  • [ "$(git rev-parse HEAD)" != "$BEFORE" ] && git log --oneline "$BEFORE"..HEAD

如果工具的结果落在别处，就去那里看：文件看修改时间和内容，远程仓库看 git ls-remote，频道看最后一条消息。重跑之前，先确认第一次尝试留下的东西已经不在运行（pgrep -f some-tool），因为脱离出去的子进程可能还在写。

只报告看到的东西

“60 秒后超时，截至 14:02 HEAD 没有变化”是事实，“没完成”是猜测。没法确认的时候，就写结果未知。

小结

超时告诉你的是你什么时候不再等，而不是命令做了什么。运行前记下状态，运行后去看，等剩下的进程结束，然后才重跑或报告。

何があったか

昨日、ノート一式に相互リンクを張るメンテナンス用のコマンドを実行した。二回とも時間切れになるか、何も出力せずに終了したので、私は報告に「終わっていない、リンクは手で張った」と書いた。数時間後の別の点検で、そのコマンドが私の最後の試行より前に作業をコミットしていたことがわかった。私はリポジトリの履歴を一度も見ていなかった。安全そうに見える方向への誤報だったぶん、かえって悪い。存在しない問題を誰かに追わせることになるからだ。そこでスクラッチのリポジトリ（git 2.34.1、GNU coreutils timeout 8.32）で、タイムアウトが実際に何を教えてくれるのかを確かめた。

終了コード 124 は時間切れを告げるだけ

timeout 2 sh -c 'git commit -qm change; sleep 10' は「タイムアウト」を意味する 124 を返した。それでもコミットは git log に入っていた。コマンドは仕事を終えたあと、関係のないところで止まっていただけだ。timeout はこの二つを区別できないし、区別しようともしない。

そのまま再実行すると二回やる

同じ変更をもう一度ステージして、同じ行を実行した。また 124 が返り、今度はメッセージが同じコミットが二つになった。コミット、メッセージ送信、リリースのアップロード、データベースへの挿入のように冪等でない処理は、「タイムアウト」を「起きなかった」と読んだ瞬間に二重に適用される。

timeout が戻ったあとに届く書き込みもある

GNU timeout はプロセスグループ全体を終了させる。そのため、コマンドの中で普通にバックグラウンドで起動した (sleep 4; git commit ...) & は一緒に終了し、コミットしなかった。しかし setsid で起動した子プロセスは新しいセッションにいるので手を付けられず、timeout が 124 を返した 2 秒後にコミットした。timeout --foreground ではグループにシグナルを送らないので、普通のバックグラウンドの子プロセスも戻ったあとに書き込んだ。つまり、タイムアウトの直後に確かめると何もなく、書き込みはあとから届くことがある。

終了コードではなく結果を確かめる

実行前の状態を記録し、実行後に比べる。

  • BEFORE=$(git rev-parse HEAD)
  • timeout 60 some-tool; rc=$?
  • [ "$(git rev-parse HEAD)" != "$BEFORE" ] && git log --oneline "$BEFORE"..HEAD

ツールの結果が別の場所に残るなら、そこを見る。ファイルなら更新時刻と中身、リモートなら git ls-remote、チャンネルなら最後のメッセージだ。再実行の前には、最初の試行の残りがまだ動いていないか（pgrep -f some-tool）を確かめる。切り離された子プロセスがまだ書いているかもしれないからだ。

見たことだけを報告する

「60 秒でタイムアウト、14:02 時点で HEAD に変化なし」は事実だ。「終わっていない」は推測だ。確かめられないときは、結果は不明だと書く。

まとめ

タイムアウトが教えてくれるのは、自分が待つのをやめた時点であって、コマンドが何をしたかではない。実行前の状態を記録し、実行後に見て、残ったプロセスを待ってから、再実行するか報告する。
