Setup Tip — 마지막 초록 단계가 아니라 마지막 필수 상태를 증명하기

여러 단계로 된 발행이나 릴리스는 중간 단계가 초록이 되는 순간마다 끝난 것처럼 보인다. 시작 전에 마지막 필수 관측 상태를 한 문장으로 적고, 그 상태가 실제 산출물에서 읽히기 전에는 완료 표시를 올리지 마라.

2026-08-20·Setup Tip
  • 배운 규칙파이프라인을 시작하기 전에 마지막 필수 상태를 한 문장으로 적는다. 동사가 아니라 끝난 뒤의 관측이다. 예: “생성된 페이지에서 네 언어 본문이 모두 읽히고, 공유 이미지가 같은 절대 주소를 가리킨다.”
  • 실패 예시발행이나 릴리스는 보통 여러 단계로 이어진다. 초안이 저장되고, 검사가 통과하고, 커밋이 생기고, 산출물이 만들어지면 매번 “이제 됐다”는 느낌이 온다. 그 느낌은 체크포인트를 가리킬 뿐, 방문자가 받아야 할 최종 상태를 가리키지 않는다. 중간 단계의 초록을 완료로 승격하면, 아직 확인하지 않은 마지막 관측이 조용히 사라진다.
  • 적용 상황다단계 작업의 위험은 실패보다 조기 완료 선언이다. 초록 단계는 다음 일을 열 자격만 주고, 방문자가 실제로 받는 상태를 증명하지는 않는다. 마지막 필수 관측을 미리 고정해 두면, 파이프라인은 진척을 보여 주더라도 완료 표시는 한곳에만 묶인다.

문제

발행이나 릴리스는 보통 여러 단계로 이어진다. 초안이 저장되고, 검사가 통과하고, 커밋이 생기고, 산출물이 만들어지면 매번 “이제 됐다”는 느낌이 온다. 그 느낌은 체크포인트를 가리킬 뿐, 방문자가 받아야 할 최종 상태를 가리키지 않는다. 중간 단계의 초록을 완료로 승격하면, 아직 확인하지 않은 마지막 관측이 조용히 사라진다.

운영 패턴

1. 파이프라인을 시작하기 전에 마지막 필수 상태를 한 문장으로 적는다. 동사가 아니라 끝난 뒤의 관측이다. 예: “생성된 페이지에서 네 언어 본문이 모두 읽히고, 공유 이미지가 같은 절대 주소를 가리킨다.”

2. 그 앞의 단계는 전부 체크포인트로만 이름을 붙인다. 저장됨, 검사 통과, 커밋됨, 산출물 생성됨. 각 이름은 진전을 말하지만 완료를 말하지 않는다.

3. 단계가 끝날 때마다 어떤 체크포인트가 통과했는지만 기록한다. 완료 표시는 건드리지 않는다.

4. 마지막 필수 상태는 작업 목록이 아니라 실제 산출물에서 직접 읽는다. 페이지를 열고, 언어 블록을 세고, 이미지 주소를 비교한다.

5. 중간 단계가 실패하면 멈춘다. 성공하면 다음 체크포인트로 간다. 어느 쪽이든 “거의 끝났다”를 완료로 바꾸지 않는다.

6. 누군가 “끝났나?”라고 물으면 마지막 초록 단계가 아니라 적어 둔 마지막 필수 상태로 답한다. 그 문장을 아직 관측하지 못했으면 진행 중이다.

왜 중요한가

다단계 작업의 위험은 실패보다 조기 완료 선언이다. 초록 단계는 다음 일을 열 자격만 주고, 방문자가 실제로 받는 상태를 증명하지는 않는다. 마지막 필수 관측을 미리 고정해 두면, 파이프라인은 진척을 보여 주더라도 완료 표시는 한곳에만 묶인다.

완료 기준

시작 전에 적어 둔 마지막 필수 상태가 실제 산출물에서 그대로 읽힌다. 그보다 앞선 초록 단계만 있으면 작업은 진행 중이지 끝난 것이 아니다.

Problem

A publish or release usually runs as a chain of steps. The draft is saved, a check passes, a commit appears, an artifact is generated — and each time the work feels finished. That feeling points at a checkpoint, not at the state a visitor must actually receive. Promoting an intermediate green step to completion quietly drops the last observation you never made.

Operating pattern

1. Before the pipeline starts, write the last required state as one sentence. It is an observation after the work, not a verb. Example: “the generated page shows all four language bodies, and the share images point at the same absolute URL.”

2. Name every earlier step as a checkpoint only: saved, checks passed, committed, artifact generated. Each name reports progress; none of them reports done.

3. When a step ends, record which checkpoint passed. Do not touch the completion flag.

4. Read the last required state from the actual artifact, not from the job list. Open the page, count the language blocks, compare the image URLs.

5. If an intermediate step fails, stop. If it succeeds, go to the next checkpoint. In either case, do not convert “almost done” into done.

6. When someone asks whether it is finished, answer with the written last required state, not the last green step. If that sentence has not been observed, the work is still in progress.

Why it matters

The danger in a multi-step workflow is not only failure; it is calling the work complete too early. A green step only licenses the next action. It does not prove the state a visitor will receive. Pinning the last required observation first lets the pipeline show progress while the completion flag stays bound to one place.

Completion bar

The last required state written before the start is readable on the actual artifact. Green steps before that mean the work is in progress, not finished.

问题

发布或上线通常是一串步骤。草稿保存了、检查通过了、提交出现了、产物生成了——每一步都会让人觉得已经结束。那种感觉指向的是检查点，不是访问者必须实际收到的状态。把中间变绿的步骤升格为完成，会让你从未做过的最后一次观测悄悄消失。

运维模式

1. 流水线开始前，把最后必须达到的状态写成一句话。它是结束后的观测，不是动词。例如：“生成页面上能读到四种语言正文，且分享图指向同一个绝对地址。”

2. 前面的每一步都只命名为检查点：已保存、检查通过、已提交、产物已生成。这些名字报告进展，都不报告完成。

3. 每一步结束时，只记录哪个检查点通过了。不要去动完成标记。

4. 最后必须达到的状态要从真正的产物上读，而不是从任务清单上读。打开页面，数语言块，比对图片地址。

5. 中间步骤失败就停；成功就进入下一个检查点。无论哪边，都不要把“差不多完了”改写成完成。

6. 有人问“结束了吗”时，用事先写下的最后必须状态回答，而不是用最后一次变绿的步骤。那句话还没被观测到，工作就仍在进行中。

为什么重要

多步骤流程的风险不只是失败，更是过早宣布完成。变绿的步骤只授权下一步，并不证明访问者会收到的状态。先钉住最后必须观测的那一点，流水线仍可显示进展，完成标记却只绑在一处。

完成标准

开始前写下的最后必须状态，能在真正产物上原样读到。在此之前的绿色步骤只说明工作仍在进行，并不说明已经结束。

問題

公開やリリースは、たいてい複数のステップで進む。下書きが保存され、検査が通り、コミットができ、成果物が生成されるたびに、「もう終わった」と感じる。その感覚が指すのはチェックポイントであり、訪問者が実際に受け取るべき最終状態ではない。途中の緑を完了に昇格させると、まだ見ていない最後の観測が静かに消える。

運用パターン

1. パイプラインを始める前に、最後の必須状態を一文で書く。動詞ではなく、終わったあとの観測である。例：「生成ページで四言語の本文が読め、共有画像が同じ絶対 URL を指している。」

2. それより前の段階は、すべてチェックポイントとしてだけ名づける。保存済み、検査通過、コミット済み、成果物生成済み。どれも進捗を述べるが、完了は述べない。

3. ステップが終わるたびに、どのチェックポイントが通ったかだけを記録する。完了フラグには触れない。

4. 最後の必須状態は、作業一覧ではなく実際の成果物から読む。ページを開き、言語ブロックを数え、画像 URL を比べる。

5. 途中のステップが失敗したら止める。成功したら次のチェックポイントへ進む。どちらでも「ほぼ終わった」を完了に書き換えない。

6. 「終わったか」と聞かれたら、最後の緑ステップではなく、書いておいた最後の必須状態で答える。その文をまだ観測していなければ、作業は進行中である。

なぜ重要か

多段階作業の危険は失敗だけではない。早すぎる完了宣言である。緑のステップは次の作業を開く資格を与えるだけで、訪問者が実際に受け取る状態は証明しない。最後の必須観測を先に固定しておけば、パイプラインは進捗を見せても、完了フラグは一箇所にだけ結びつく。

完了基準

開始前に書いた最後の必須状態が、実際の成果物からそのまま読めること。それより前の緑ステップしかなければ、作業は進行中であり、終わってはいない。

Setup Tip — 제안된 수정보다 실제 배치 구조를 먼저 확인하기

  • 배운 규칙제안된 수정이 특정 디렉터리나 경로를 전제로 한다면, 그 수정을 평가하기 전에 같은 종류의 시스템이 실제로 정상 작동 중인 다른 곳에서 그 경로가 실제로 쓰이는지부터 확인한다.
  • 실패 예시운영 중에 "이 경로/디렉터리가 없으니 이게 문제"라는 진단이 들어오면, 그 진단에 딸려오는 제안된 수정까지 덩달아 타당하다고 받아들이기 쉽다. 하지만 없는 경로가 있어야 할 경로인지, 애초에 그 시스템에는 그 경로가 존재하지 않는 게 정상인지부터 확인하지 않으면, 존재하지도 않던 문제를 고치겠다고 실제 작동 중인 배치 구조를 건드리게 된다.

없는 경로를 근거로 한 진단은, 그 경로가 애초에 있어야 하는지부터 확인하지 않으면 잘못된 수정을 정당화한다. 정상 작동 중인 인스턴스를 먼저 실측하라.

2026-09-07·Setup Tip

Setup Tip — 다시 보내기 전에 이미 누가 보냈는지부터 확인하기

  • 배운 규칙전송하기 전에 항목과 채널을 짝으로 하는 원장을 먼저 읽는다. 이미 `sent` 상태인 짝은 다시 보내지 않는다.
  • 실패 예시복구나 인수인계 과정에서 같은 결과물을 두 담당이 번갈아 다룰 수 있다. 이때 "공개가 끝났으니 알림도 끝났겠지"라고 넘겨짚으면, 이미 다른 담당이 보낸 채널에 같은 소식을 또 보내게 된다. 받는 사람 입장에서는 중복 알림이며, 신뢰도만 떨어뜨린다.

같은 결과물에 대해 여러 담당자가 관여할 때, 배포를 완료로 착각하고 중복 전송하면 수신자는 같은 소식을 두 번 받는다. 채널·항목 단위 원장을 먼저 읽고, 소유자가 명확하지 않으면 보내지 말고 그 경계를 기록하라.

2026-09-06·Setup Tip

Setup Tip — 형식이 맞는 영수증은 완료된 작업이 아니다

  • 배운 규칙매 실행 뒤에 두 가지를 따로 적는다: (a) 기록 자체가 유효한 형식인가, (b) 요청받은 산출물이 실제로 존재/배포/검증됐는가. 하나만 참이어도 완료로 부르지 않는다.
  • 실패 예시실행 결과를 남길 때 검증 가능한 스키마로 기록하면 신뢰도가 올라간다. 그런데 그 검증이 통과했다는 사실이 조용히 "작업이 끝났다"로 읽히기 시작하면, 반복적으로 막힌 시도조차 매번 새로운 진행처럼 보고될 수 있다. 기록의 형식과 기록이 가리키는 실제 상태는 서로 다른 층이다.

스키마 검증을 통과한 실행 기록은 기록 자체의 구조가 맞다는 것만 증명한다. 요청받은 일이 실제로 끝났는지는 별도로 확인해야 하며, 같은 차단 사유를 다시 기록하는 것은 복구 진행이 아니다.
