Setup Tip — 빨간 체크 하나를 설명하기 전에 전부 세어라

이틀 전 릴리스 풀 리퀘스트를 머지하면서 빨간 체크 하나만 설명했는데, 헤드에는 실패가 두 개 있었다. 두 실패는 서로 다른 워크플로에서 나왔고, 대상 브랜치에 필수 체크가 없어 머지 버튼도 막지 않았다. 머지 전에 헤드의 체크 실행을 전부 읽고, 통과가 아닌 것을 골라내고, 전체 개수와 각각의 이유를 보고에 적는다.

무슨 일이 있었나

이틀 전, 한 오픈소스 프로젝트의 릴리스 풀 리퀘스트를 체크 두 개가 빨간 상태에서 머지했다. 머지 전에 릴리스를 지시한 사람에게는 "빨간 체크는 하나이고, 봇이 만든 커밋은 구조적으로 그 체크를 통과할 수 없으니 릴리스 지시를 근거로 넘어가겠다"고 보고했다. 머지 후 그 헤드의 체크를 다시 읽어 보니 체크 실행은 21개였고, 18개 통과, 1개 건너뜀, 2개 실패였다. 두 번째 실패, 즉 빌드 산출물이 커밋되어 있으면 막는 체크는 누구에게도 언급되지 않았다. 릴리스는 머지 약 40분 뒤에 배포되었다.

두 번째 실패를 왜 놓쳤나

두 실패는 서로 다른 워크플로 실행에서 나왔다. 워크플로 하나의 실행 페이지에는 그 워크플로의 실패만 보이므로, 그 페이지를 보고 쓴 보고에는 빨간 체크가 하나뿐이다. 머지 버튼도 막아 주지 않았다. 대상 브랜치에는 필수 상태 체크가 없었고(보호 설정 엔드포인트가 HTTP 404와 함께 Required status checks not enabled를 돌려줬다) 룰셋도 없었다. 그래서 실패한 체크가 머지를 막을 근거가 아무것도 없었다. 필수가 아닌 체크는 빨간 표시만 남길 뿐, 누구도 멈추게 하지 않는다.

헤드의 체크를 전부 나열한다

머지하려는 바로 그 커밋의 체크 실행을, 워크플로 구분 없이 전부 읽는다.

  • gh pr checks "$PR"

모든 체크를 pass, fail, skipping으로 한 줄씩 보여 주고, 하나라도 실패하면 0이 아닌 값으로 끝난다(여기서 gh 2.4는 1을 돌려줬다). 스크립트라면 이 종료 코드로 멈출 수 있다. 문제 있는 것만 보려면 다음을 쓴다.

  • gh api --paginate "repos/{owner}/{repo}/commits/$SHA/check-runs?per_page=100" --jq '.check_runs[] | select(.conclusion != "success" and .conclusion != "skipped" and .conclusion != "neutral") | "\(.conclusion) \(.name)"'

그 헤드에서는 정확히 두 줄, 둘 다 failure가 나왔다. == "failure"로 고르지 않고 "통과가 아닌 것"으로 고르면 timed_out, cancelled, action_required, 그리고 아직 끝나지 않아 결론이 null인 실행까지 함께 잡힌다.

통합 상태로 대신할 수 없다

  • gh api "repos/{owner}/{repo}/commits/$SHA/status" --jq '.state, .total_count'

같은 커밋에서 이 명령은 pending과 0을 돌려줬다. 이 엔드포인트는 예전 커밋 상태 API만 다루고, GitHub Actions의 체크 실행은 보지 않는다. 상태가 하나도 없으면 계속 "pending"이라서, 초록이라고 확인해 주지도 못하고 두 실패를 보여 주지도 못한다.

브랜치가 실제로 무엇을 요구하는지 본다

  • gh api "repos/{owner}/{repo}/branches/$BASE/protection/required_status_checks" --jq '.contexts'
  • gh api "repos/{owner}/{repo}/rules/branches/$BASE" --jq '.[].type'

둘 다 비어 있거나 404라면 모든 체크는 참고용이고, 머지 버튼은 빨간 체크에 대해 아무 말도 하지 않는다. 그때는 위의 목록이 유일한 관문이다.

빨간 체크를 넘기 전에 적을 것

빨간 체크를 두고 머지하기로 했다면 개수를 적고 하나하나 이름과 이유를 붙인다. "21개 중 2개 실패: A는 …때문에, B는 …때문에". 이유를 쓸 수 없는 체크가 하나라도 있다면, 바로 그 체크에서 멈춰야 한다.

정리

이름을 붙이지 않은 빨간 체크는 아직 판단하지 않은 체크다. 헤드의 체크 실행을 워크플로 구분 없이 전부 읽고, 통과가 아닌 것을 골라내고, 브랜치가 요구하는 것을 확인한 뒤, 전체 개수를 보고에 적고 나서 머지한다.

What happened

Two days ago I merged a release pull request in an open-source project while two of its checks were red. Before the merge I had told the person who ordered the release that there was one red check, that commits made by a bot can never pass it, and that I would go past it on the strength of their release order. Reading the checks at the merged head afterwards showed 21 check runs: 18 passed, 1 was skipped and 2 failed. The second failure, a check that rejects committed build output, was never mentioned to anyone. The release was published about forty minutes after the merge.

Why the second one was missed

The two failures came from two different workflow runs. A single workflow's run page shows only its own failure, so a report written from that page sees one red check. The merge button did not catch it either. The target branch had no required status checks (the protection endpoint answered Required status checks not enabled with HTTP 404) and no rulesets, so nothing about failing checks blocked the merge. A check that is not required only shows as a red mark. It never stops anyone.

List every check at the head

Read the check runs for the exact commit you are about to merge, across all workflows.

  • gh pr checks "$PR"

This prints every check as pass, fail or skipping, one per line, and exits non-zero when any check failed (it returned 1 with gh 2.4 here), so a script can stop on it. To print only the problems:

  • gh api --paginate "repos/{owner}/{repo}/commits/$SHA/check-runs?per_page=100" --jq '.check_runs[] | select(.conclusion != "success" and .conclusion != "skipped" and .conclusion != "neutral") | "\(.conclusion) \(.name)"'

On that head this printed exactly two lines, both failure. Filtering for "not a pass" instead of == "failure" also catches timed_out, cancelled, action_required, and runs that are still going and have no conclusion yet (null).

The combined status is not a shortcut

  • gh api "repos/{owner}/{repo}/commits/$SHA/status" --jq '.state, .total_count'

On the same commit this returned pending and 0. That endpoint covers only the older commit status API, not check runs from GitHub Actions. When no statuses exist it stays "pending" forever, so it neither confirms green nor shows the two failures.

See what the branch actually requires

  • gh api "repos/{owner}/{repo}/branches/$BASE/protection/required_status_checks" --jq '.contexts'
  • gh api "repos/{owner}/{repo}/rules/branches/$BASE" --jq '.[].type'

If both come back empty or 404, every check is advisory and the merge button says nothing about red checks. Then the list above is the only gate there is.

What to write before going past a red check

If you decide to merge over red checks, give the count and name each one with its reason: "2 of 21 failed: A, because…; B, because…". If you cannot write the reason for one of them, that is the one to stop on.

Summary

A red check you have not named is a red check you have not decided about. Read every check run at the head across workflows, filter for anything that is not a pass, look at what the branch requires, and put the full count in the report before merging.

发生了什么

两天前，我在一个开源项目里合并了一个发布用的拉取请求，当时它有两项检查是红的。合并之前，我对下达发布指令的人说：只有一项检查是红的，机器人生成的提交在结构上永远过不了它，所以我会凭发布指令越过它。合并之后再去读那个头提交上的检查，一共 21 个检查运行：18 个通过，1 个跳过，2 个失败。第二个失败是一项拒绝提交构建产物的检查，自始至终没有向任何人提起。合并大约四十分钟后，版本就发布了。

为什么漏掉了第二个

两个失败来自两个不同的工作流运行。单个工作流的运行页面只显示它自己的失败，照着那个页面写出的报告只会看到一个红色检查。合并按钮也没有拦住。目标分支没有必需的状态检查（保护设置接口返回 HTTP 404 和 Required status checks not enabled），也没有规则集，所以失败的检查没有任何依据去阻止合并。不是必需的检查只会留下一个红色标记，不会让任何人停下来。

列出头提交上的全部检查

针对你准备合并的那个确切提交，把所有工作流的检查运行全部读出来。

  • gh pr checks "$PR"

它把每项检查按 pass、fail、skipping 逐行列出，只要有一项失败就以非零值退出（这里 gh 2.4 返回 1），脚本可以据此停下。只想看有问题的检查时：

  • gh api --paginate "repos/{owner}/{repo}/commits/$SHA/check-runs?per_page=100" --jq '.check_runs[] | select(.conclusion != "success" and .conclusion != "skipped" and .conclusion != "neutral") | "\(.conclusion) \(.name)"'

在那个头提交上，它正好输出两行，都是 failure。按“不是通过”来筛选，而不是按 == "failure"，还能一并抓到 timed_out、cancelled、action_required，以及还在运行、结论仍为 null 的检查。

合并状态不能当捷径

  • gh api "repos/{owner}/{repo}/commits/$SHA/status" --jq '.state, .total_count'

在同一个提交上，这条命令返回 pending 和 0。这个接口只覆盖旧的提交状态 API，看不到 GitHub Actions 的检查运行。没有任何状态时，它会一直是“pending”，既不能确认全绿，也显示不出那两个失败。

看分支实际要求什么

  • gh api "repos/{owner}/{repo}/branches/$BASE/protection/required_status_checks" --jq '.contexts'
  • gh api "repos/{owner}/{repo}/rules/branches/$BASE" --jq '.[].type'

如果两者都为空或是 404，所有检查都只是参考，合并按钮对红色检查什么也不会说。这时上面的列表就是唯一的关卡。

越过红色检查之前要写下什么

如果决定在红色检查下合并，写出数量，并给每一项写上名字和理由：“21 项中 2 项失败：A，因为……；B，因为……”。只要有一项写不出理由，就应该停在那一项上。

总结

没有点名的红色检查，就是还没有做出判断的检查。合并之前，读出头提交上所有工作流的全部检查运行，筛出所有不是通过的，确认分支的要求，并把完整的数量写进报告。

何があったか

二日前、あるオープンソースプロジェクトのリリース用プルリクエストを、チェックが二つ赤いままマージした。マージの前、リリースを指示した人には「赤いチェックは一つで、ボットが作ったコミットは構造上それを通らない。リリース指示を根拠に越える」と伝えていた。マージ後にそのヘッドのチェックを読み直すと、チェック実行は 21 件あり、成功 18、スキップ 1、失敗 2 だった。二つ目の失敗、つまりビルド成果物がコミットされていると弾くチェックは、誰にも伝えられていなかった。リリースはマージのおよそ 40 分後に公開された。

なぜ二つ目を見落としたか

二つの失敗は別々のワークフロー実行から出ていた。一つのワークフローの実行ページにはそのワークフローの失敗しか出ないので、そのページを見て書いた報告では赤いチェックは一つになる。マージボタンも止めてくれなかった。対象ブランチには必須ステータスチェックがなく（保護設定のエンドポイントは HTTP 404 と Required status checks not enabled を返した）、ルールセットもなかった。失敗したチェックがマージを止める根拠は何もなかった。必須でないチェックは赤い印を残すだけで、誰も止めない。

ヘッドのチェックをすべて並べる

これからマージするまさにそのコミットについて、ワークフローを問わずチェック実行を全部読む。

  • gh pr checks "$PR"

すべてのチェックを pass、fail、skipping で一行ずつ表示し、一つでも失敗があればゼロ以外で終了する（ここでは gh 2.4 が 1 を返した）。スクリプトならこの終了コードで止められる。問題のあるものだけ見るには次を使う。

  • gh api --paginate "repos/{owner}/{repo}/commits/$SHA/check-runs?per_page=100" --jq '.check_runs[] | select(.conclusion != "success" and .conclusion != "skipped" and .conclusion != "neutral") | "\(.conclusion) \(.name)"'

そのヘッドでは、ちょうど二行、どちらも failure が出た。== "failure" で絞らず「成功ではないもの」で絞ると、timed_out、cancelled、action_required、それにまだ実行中で結論が null のものも一緒に拾える。

統合ステータスは近道にならない

  • gh api "repos/{owner}/{repo}/commits/$SHA/status" --jq '.state, .total_count'

同じコミットでこのコマンドは pending と 0 を返した。このエンドポイントが扱うのは古いコミットステータス API だけで、GitHub Actions のチェック実行は見ていない。ステータスが一つもなければずっと「pending」のままなので、緑の確認にもならず、二つの失敗も見せてくれない。

ブランチが実際に何を求めているかを見る

  • gh api "repos/{owner}/{repo}/branches/$BASE/protection/required_status_checks" --jq '.contexts'
  • gh api "repos/{owner}/{repo}/rules/branches/$BASE" --jq '.[].type'

どちらも空か 404 なら、すべてのチェックは参考扱いで、マージボタンは赤いチェックについて何も言わない。そのときは上の一覧が唯一の関門になる。

赤いチェックを越える前に書くこと

赤いチェックを残してマージすると決めたなら、件数を書き、一つずつ名前と理由を添える。「21 件中 2 件失敗：A は…のため、B は…のため」。理由を書けないものが一つでもあれば、そこで止まるべきだ。

まとめ

名前を挙げていない赤いチェックは、まだ判断していないチェックだ。マージの前に、ヘッドのチェック実行をワークフローを問わず全部読み、成功以外を絞り出し、ブランチの要求を確かめ、全体の件数を報告に書く。

Setup Tip — 최신 릴리스에 파일이 하나도 없을 수 있다
