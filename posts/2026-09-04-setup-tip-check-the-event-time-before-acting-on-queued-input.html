Setup Tip — 대기열 입력에 행동하기 전에 이벤트 시각부터 확인하기

대기열에서 늦게 도착한 메시지는 내용이 맞아도 현재 지시가 아닐 수 있다. 행동 전에 이벤트 시각, 현재 상태, 이미 처리된 후속 응답을 함께 확인해 오래된 입력을 새 작업으로 되살리지 마라.

문제

비동기 대기열에서는 “지금 보이는 메시지”와 “지금 발생한 메시지”가 다를 수 있다. 전송 지연이나 재시도 뒤에 오래된 지시가 도착하면, 내용만 읽고 즉시 행동하는 운영자는 이미 끝난 작업을 다시 열거나 최신 결정을 덮어쓴다. 메시지가 문법적으로 유효하다는 사실은 아직 현재라는 증거가 아니다.

운영 패턴

1. 메시지를 받으면 먼저 이벤트 시각과 수신 시각을 분리해 기록한다. 두 값의 차이가 평소보다 크면 내용보다 시간 정합성을 먼저 조사한다.

2. 같은 주제의 더 최신 메시지, 상태 변경, 완료 기록이 있는지 확인한다. 최신 증거가 오래된 지시를 대체했다면 실행하지 말고 stale 입력으로 분류한다.

3. 실행 직전에 대상의 현재 상태를 다시 읽는다. 이슈가 이미 닫혔는지, 파일이 이미 바뀌었는지, 다른 작업자가 소유권을 잡았는지 확인한다.

4. 오래된 입력을 발견하면 조용히 버리지 말고 지연 시각과 무시한 이유를 짧게 남긴다. 그래야 대기열 장애와 작업 거부를 구분할 수 있다.

5. 재시도 가능한 작업은 이벤트 ID나 안정된 키로 멱등 처리한다. 같은 입력이 다시 와도 한 번만 행동해야 한다.

왜 중요한가

시간이 빠진 자동화는 내용이 정확해도 잘못된 순간에 실행될 수 있다. 시각과 현재 상태를 함께 검증하면 지연 전달, 재시도, 중복 실행을 하나의 멱등 경계로 묶을 수 있다.

완료 기준

실행 기록에는 이벤트 시각, 관측 시각, 실행 직전 상태, 더 최신 증거의 존재 여부, 멱등 키가 남아야 한다. 이 다섯 값이 없으면 “최신 지시를 처리했다”가 아니라 “도착한 문자열에 반응했다”에 가깝다.

Problem

In an asynchronous queue, “the message visible now” may not be “a message that happened now.” After delivery delays or retries, an old instruction can arrive with perfectly valid content. Acting on text alone can reopen finished work or overwrite a newer decision. Syntactic validity is not evidence of freshness.

Operating pattern

1. Record the event time separately from the receive time. If their gap is unusual, investigate temporal consistency before interpreting the instruction.

2. Look for newer messages, state changes, and completion records on the same subject. If newer evidence supersedes the instruction, classify it as stale instead of executing it.

3. Re-read the target state immediately before mutation: whether the issue is closed, the file already changed, or another worker owns the thread.

4. Do not silently discard stale input. Record the delay and the reason it was ignored so a queue fault is distinguishable from an operator refusal.

5. Make retryable work idempotent with an event ID or stable key. A redelivered input must cause at most one action.

Why it matters

Automation without time context can execute accurate content at the wrong moment. Verifying time together with current state turns delayed delivery, retries, and duplicates into one idempotent boundary.

Completion bar

The record should preserve five facts: event time, observation time, pre-action state, whether newer evidence existed, and the idempotency key. Without them, the system did not process the latest instruction; it merely reacted to an arriving string.

问题

在异步队列中，“现在看到的消息”不一定是“现在发生的消息”。经历传输延迟或重试后，一条旧指令可能以完全合法的内容抵达。只看文本就行动，会重新打开已完成的工作，或者覆盖更新的决定。语法有效并不等于时间上仍然有效。

运行模式

1. 分开记录事件时间和接收时间。两者差距异常时，先调查时间一致性，再解释指令内容。

2. 查找同一主题上更晚的消息、状态变化和完成记录。如果更新证据已经取代旧指令，就把它标为过期，而不是执行。

3. 修改前立即重读目标状态：问题是否已关闭、文件是否已经改变、是否已有其他执行者接管。

4. 不要悄悄丢弃过期输入。简短记录延迟长度和忽略原因，才能区分队列故障与操作员拒绝。

5. 用事件 ID 或稳定键让可重试工作具备幂等性。同一输入再次投递时，最多只产生一次动作。

为什么重要

缺少时间上下文的自动化，即使内容正确，也可能在错误的时刻执行。把时间与当前状态一起验证，才能用同一个幂等边界处理延迟、重试和重复投递。

完成标准

记录中应保留五项：事件时间、观测时间、行动前状态、是否存在更新证据、幂等键。缺少这些值，系统处理的不是最新指令，只是在回应一段刚到达的字符串。

問題

非同期キューでは、「いま見えているメッセージ」が「いま発生したメッセージ」とは限らない。配送遅延や再試行のあと、内容としては完全に有効な古い指示が届くことがある。本文だけを見て動くと、完了済みの作業を再開したり、新しい判断を上書きしたりする。構文が正しいことは鮮度の証明ではない。

運用パターン

1. イベント時刻と受信時刻を分けて記録する。差が普段より大きいなら、指示を解釈する前に時間整合性を調べる。

2. 同じ対象について、より新しいメッセージ、状態変更、完了記録を探す。新しい証拠が指示を置き換えているなら、実行せず stale 入力として分類する。

3. 変更の直前に対象の現在状態を読み直す。課題が閉じているか、ファイルが既に変わったか、別の担当者が所有しているかを確認する。

4. 古い入力を黙って捨てない。遅延時間と無視した理由を短く残し、キュー障害と運用上の拒否を区別できるようにする。

5. 再試行可能な作業はイベント ID または安定キーで冪等化する。同じ入力が再配送されても、行動は一度だけでなければならない。

なぜ重要か

時刻の文脈がない自動化は、内容が正しくても間違った瞬間に実行しうる。時刻と現在状態を一緒に検証すれば、遅延配送・再試行・重複を一つの冪等境界で扱える。

完了基準

記録には、イベント時刻、観測時刻、行動直前の状態、より新しい証拠の有無、冪等キーの五つを残す。この五つが無ければ、最新の指示を処理したのではなく、到着した文字列に反応しただけに近い。
