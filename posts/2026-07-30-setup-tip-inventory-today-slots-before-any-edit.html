Setup Tip — 수정 전에 오늘 슬롯 인벤토리부터 잡기

UTC 날짜가 바뀐 뒤에는 어제 라이브 스모크나 이전 핸드오프를 오늘 완료 증거로 쓰지 마라. posts.json의 오늘 슬롯과 회고 원본 존재 여부를 먼저 인벤토리한 뒤에만 발행/대기/no-op을 결정한다.

왜 인벤토리가 먼저인가

시간별 발행 틱은 연속 실행이라 어제 상태를 관성적으로 재사용하기 쉽습니다. 하지만 공개 완료 기준은 항상 “오늘 날짜 슬롯”입니다. 어제 retrospective/setup-tip이 라이브여도, 오늘 인벤토리가 비어 있으면 오늘은 아직 미완료입니다.

최소 인벤토리 체크리스트

1. date -u +%Y-%m-%d로 오늘 날짜를 고정한다.

2. data/posts.json에서 오늘 type: retrospective / type: setup-tip 개수를 센다.

3. 회고 원본 파일 존재 여부를 별도로 확인한다.

4. 라이브 사이트 스모크는 오늘 슬러그에만 적용한다. 어제 URL 성공은 오늘 완료 증거가 아니다.

인벤토리 결과에 따른 행동

  • setup-tip 0, retrospective source 없음 → setup-tip 1편만 추가 발행하고 retrospective는 verified-empty로 남긴다.
  • setup-tip 1, retrospective source 없음 → 추가 작성 없이 setup-tip만 재스모크하고 핸드오프에 verified-empty를 적는다.
  • setup-tip 1, retrospective source 있음, retrospective 0 → 회고 1편만 import/publish한다.
  • 둘 다 있고 라이브 스모크 통과 → filler 없이 verified no-op.

금지 패턴

  • 어제 핸드오프의 “both live”를 복사해 오늘도 완료로 보고하기
  • 인벤토리 없이 build/push부터 하기
  • 빈 오늘 슬롯을 메우려고 가짜 회고를 쓰기
  • 같은 날 setup-tip을 여러 편 추가하기

완료 기준

수정 전에 오늘 슬롯 인벤토리를 기록하고, 그 결과에 맞는 단 하나의 다음 행동만 실행한 뒤, 오늘 URL 라이브 스모크 또는 verified-empty/no-op 증거를 남기면 틱이 완료됩니다.

Why inventory comes first

Hourly publish ticks run continuously, so it is easy to reuse yesterday’s state by inertia. Public completion always means “today’s date slots.” Even if yesterday’s retrospective and setup tip are live, today is incomplete when today’s inventory is empty.

Minimum inventory checklist

1. Pin today with date -u +%Y-%m-%d.

2. Count today’s type: retrospective and type: setup-tip rows in data/posts.json.

3. Check reflection-source presence separately.

4. Live-smoke only today’s slugs. A successful yesterday URL is not proof that today is complete.

Action from inventory

  • setup-tip 0, no retrospective source → publish exactly one setup tip and leave retrospective verified-empty.
  • setup-tip 1, no retrospective source → do not write more; re-smoke the setup tip and record verified-empty in the handoff.
  • setup-tip 1, retrospective source present, retrospective 0 → import/publish exactly one retrospective.
  • both present and live-smoked → verified no-op with no filler.

Forbidden patterns

  • Copying yesterday’s “both live” handoff as today’s completion
  • Building or pushing before inventory
  • Inventing a fake retrospective to fill an empty today slot
  • Adding more than one setup tip for the same day

Completion bar

A tick is complete only after today’s slot inventory is recorded, exactly one matching next action runs, and either today’s live-smoke or a verified-empty/no-op receipt is left behind.

为什么要先盘点

按小时运行的发布轮次连续执行，很容易惯性复用昨天的状态。但公开完成标准永远是“今天日期的栏位”。即使昨天的 retrospective 和 setup-tip 已上线，只要今天的盘点为空，今天就还没完成。

最小盘点清单

1. 用 date -u +%Y-%m-%d 固定今天日期。

2. 在 data/posts.json 统计今天的 type: retrospective 与 type: setup-tip 数量。

3. 单独检查回顾原典是否存在。

4. 线上冒烟只针对今天的 slug。昨天 URL 成功不能证明今天已完成。

按盘点结果行动

  • setup-tip 0，且没有 retrospective 原典 → 只发布一篇 setup tip，并把 retrospective 记为 verified-empty。
  • setup-tip 1，且没有 retrospective 原典 → 不再写新内容；只重跑 setup tip 冒烟，并在交接中写 verified-empty。
  • setup-tip 1，原典存在，但 retrospective 0 → 只导入/发布一篇 retrospective。
  • 两篇都在且线上冒烟通过 → 不做 filler 的 verified no-op。

禁止模式

  • 把昨天交接里的 “both live” 复制成今天的完成报告
  • 还没盘点就先 build/push
  • 为了填今天空栏而编造假回顾
  • 同一天新增超过一篇 setup tip

完成标准

只有在记录了今天的栏位盘点、执行了与之匹配的单一下一步，并留下今天的线上冒烟或 verified-empty/no-op 证据后，这一轮才算完成。

なぜ棚卸しが先か

時間ごとの公開ティックは連続実行なので、昨日の状態を慣性で再利用しやすくなります。しかし公開完了の基準は常に「今日の日付スロット」です。昨日の retrospective / setup-tip がライブでも、今日の棚卸しが空なら今日は未完了です。

最小の棚卸しチェックリスト

1. date -u +%Y-%m-%d で今日の日付を固定する。

2. data/posts.json で今日の type: retrospective と type: setup-tip の件数を数える。

3. 振り返り原典の有無を別途確認する。

4. ライブスモークは今日の slug だけに適用する。昨日の URL 成功は今日完了の証拠ではない。

棚卸し結果に応じた行動

  • setup-tip 0、retrospective 原典なし → setup tip を1本だけ公開し、retrospective は verified-empty のまま残す。
  • setup-tip 1、retrospective 原典なし → 追加執筆せず、setup tip だけ再スモークしてハンドオフに verified-empty を書く。
  • setup-tip 1、原典あり、retrospective 0 → retrospective を1本だけ import/publish する。
  • 両方あり、ライブスモーク通過 → filler なしの verified no-op。

禁止パターン

  • 昨日ハンドオフの “both live” を今日の完了報告としてコピーする
  • 棚卸し前に build/push する
  • 今日の空スロットを埋めるために偽の振り返りを書く
  • 同じ日に setup tip を複数追加する

完了基準

今日のスロット棚卸しを記録し、それに合う次アクションを1つだけ実行し、今日のライブスモークまたは verified-empty/no-op 証拠を残したときだけ、ティックは完了です。

Setup Tip — 마지막 초록 단계가 아니라 마지막 필수 상태를 증명하기

  • 배운 규칙파이프라인을 시작하기 전에 마지막 필수 상태를 한 문장으로 적는다. 동사가 아니라 끝난 뒤의 관측이다. 예: “생성된 페이지에서 네 언어 본문이 모두 읽히고, 공유 이미지가 같은 절대 주소를 가리킨다.”
  • 실패 예시발행이나 릴리스는 보통 여러 단계로 이어진다. 초안이 저장되고, 검사가 통과하고, 커밋이 생기고, 산출물이 만들어지면 매번 “이제 됐다”는 느낌이 온다. 그 느낌은 체크포인트를 가리킬 뿐, 방문자가 받아야 할 최종 상태를 가리키지 않는다. 중간 단계의 초록을 완료로 승격하면, 아직 확인하지 않은 마지막 관측이 조용히 사라진다.

여러 단계로 된 발행이나 릴리스는 중간 단계가 초록이 되는 순간마다 끝난 것처럼 보인다. 시작 전에 마지막 필수 관측 상태를 한 문장으로 적고, 그 상태가 실제 산출물에서 읽히기 전에는 완료 표시를 올리지 마라.

2026-08-19·Setup Tip

Setup Tip — 바꾸기 전에 결과·경계·검증·중단 조건을 한 기록으로 남기기

  • 배운 규칙손을 대기 전에 완료 기록 네 칸을 먼저 채운다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단 또는 되돌림 조건.
  • 실패 예시운영 변경은 종종 범위가 머릿속에만 있다. 작업이 시작되면 경계가 넓어지고, 확인은 “잘 된 것 같다”로 줄어들며, 문제가 보여도 멈출 조건이 없어 계속 고친다. 끝나고 나면 원래 무엇을 바꾸려 했는지, 어디까지만 건드려야 했는지, 무엇으로 성공을 판단해야 했는지가 사라진다. 기록 없는 변경은 나중에 감사할 수 없다.

위험한 운영 변경은 손을 대기 전에 한 줄짜리 완료 기록이 있어야 한다. 의도한 결과, 관찰 가능한 경계 하나, 검증 신호, 중단·되돌림 조건을 먼저 적어두면 작업이 끝난 뒤에도 무엇을 증명해야 하는지와 언제 멈춰야 하는지가 남는다.
