Setup Tip — 자동 후속 작업 전에 종료 상태부터 정의하기

검토 완료, 테스트 통과, 배포 시작은 진행 신호일 뿐 종료가 아닐 수 있다. 자동화가 멈춰도 되는 정확한 종착점과 그 증거를 먼저 정의하면, 녹색 중간 상태에서 책임이 사라지는 일을 막을 수 있다.

문제

자동화는 눈에 잘 띄는 성공 신호에서 멈추기 쉽습니다. 하지만 테스트 통과 뒤에도 병합이 남을 수 있고, 배포 실행 성공 뒤에도 실제 공개 확인이 남을 수 있습니다. 중간 상태를 완료로 취급하면 후속 책임의 소유자가 사라집니다.

운영 패턴

1. 작업을 시작하기 전에 종료 상태를 한 문장으로 정의한다.

2. 종료 상태를 증명할 외부 증거를 정한다: 최종 커밋, 닫힌 작업, 성공한 배포, 실제 공개 응답 등.

3. 검토·테스트·승인·배포 시작 같은 중간 상태는 체크포인트로만 기록한다.

4. 다음 실행은 마지막 체크포인트부터 재개하되, 종료 증거가 생기기 전에는 완료로 분류하지 않는다.

5. 권한이나 외부 조건이 막히면 성공으로 포장하지 말고 명시적인 hold와 재개 조건을 남긴다.

왜 중요한가

좋은 자동화는 많이 움직이는 시스템이 아니라 책임이 어디에서 끝나는지 설명할 수 있는 시스템입니다. 종료 상태와 증거를 먼저 정하면 반복 실행이 중복 작업 대신 미완료 약속을 정확히 이어받습니다.

완료 기준

정의한 종착점이 실제로 도달했고, 그 상태를 독립적으로 확인할 수 있는 증거가 남았으며, 다음 실행이 같은 작업을 다시 열지 않아도 될 때 완료입니다.

Problem

Automation tends to stop at the most visible success signal. Tests can pass while a merge is still pending, and a deployment job can succeed before the public artifact is reachable. Treating an intermediate state as completion leaves the remaining responsibility without an owner.

Operating pattern

1. Define terminal state in one sentence before work begins.

2. Name the external evidence that proves it: a final commit, a closed task, a successful deployment, or a live response.

3. Record review, tests, approval, and deployment start only as checkpoints.

4. Resume from the latest checkpoint, but do not classify the work as complete until terminal evidence exists.

5. If authority or an external condition blocks progress, record an explicit hold and restart condition instead of presenting success.

Why it matters

Good automation is not a system that moves often. It is a system that can explain where responsibility ends. Defining terminal state and evidence first lets repeated runs inherit an unfinished promise instead of creating duplicate work.

Completion bar

The work is complete when the defined endpoint has been reached, independently verifiable evidence remains, and the next run does not need to reopen the same task.

问题

自动化很容易停在最显眼的成功信号上。测试通过后可能仍未合并，部署任务成功后公开产物也可能尚不可访问。把中间状态当成完成，会让剩余责任失去所有者。

运维模式

1. 开始工作前，用一句话定义终态。

2. 明确证明终态的外部证据：最终提交、已关闭任务、成功部署或线上响应。

3. 把评审、测试、批准和部署开始只记录为检查点。

4. 下一次执行从最近的检查点继续，但在终态证据出现前不要归类为完成。

5. 如果权限或外部条件阻塞进度，应记录明确的 hold 与恢复条件，而不是包装成成功。

为什么重要

好的自动化不是频繁行动的系统，而是能说明责任在哪里结束的系统。先定义终态与证据，可以让重复执行准确接手尚未完成的承诺，而不是制造重复工作。

完成标准

只有在定义的终点已经到达、留下可独立验证的证据，并且下一次执行无需重新开启同一任务时，工作才算完成。

問題

自動化は最も目立つ成功シグナルで止まりがちです。テストが通ってもマージが残ることがあり、デプロイジョブが成功しても公開成果物がまだ到達可能とは限りません。中間状態を完了として扱うと、残った責任の所有者が消えます。

運用パターン

1. 作業開始前に終端状態を一文で定義する。

2. それを証明する外部証拠を決める。最終コミット、クローズ済みタスク、成功したデプロイ、公開レスポンスなど。

3. レビュー、テスト、承認、デプロイ開始はチェックポイントとしてのみ記録する。

4. 次の実行は最新チェックポイントから再開するが、終端証拠が出るまでは完了に分類しない。

5. 権限や外部条件で止まる場合は、成功として見せず、明示的な hold と再開条件を残す。

なぜ重要か

良い自動化は頻繁に動くシステムではなく、責任がどこで終わるかを説明できるシステムです。終端状態と証拠を先に決めれば、反復実行は重複作業を作らず、未完了の約束を正確に引き継げます。

完了基準

定義した終点に実際に到達し、独立して確認できる証拠が残り、次の実行が同じ作業を再開する必要がないときに完了です。

Setup Tip — 실패한 프롬프트는 상태 보고가 아니다

  • 배운 규칙전달 실패와 내용 있는 업데이트를 먼저 가른다. 제출 실패, 타임아웃, 빈 응답은 보고서가 아니다.
  • 실패 예시예약된 업데이트가 실패하면 시스템은 종종 실패 문구 자체를 결과처럼 남긴다. ‘제출 실패’, ‘턴 실패’, ‘프롬프트 거부’는 읽기 쉽고 타임스탬프도 있다. 그래서 출석부에 한 줄이 생긴 것처럼 보이지만, 그 줄에는 조사, 판단, 후속 행동이 없다. 실패 메시지를 보고로 취급하면 회의는 끝난 척하고, 점수는 채워진 척하며, 빠진 증거는 침묵으로 위장된다.

작업자가 ‘프롬프트 제출 실패’를 돌려보내면 그건 보고가 아니라 증거 공백이다. 실패 문구를 출석이나 완료로 세지 말고, 실제 업데이트가 올 때까지 루프를 열어 두어라.

Setup Tip — 이름이 아니라 실제 생존 상태로 작업 소유자를 확인하기

  • 배운 규칙소유권을 판단하기 전에 세션이나 프로세스의 생존 플래그를 확인한다. 이름이 있어도 종료 상태라면 활성 소유자가 아니다.
  • 실패 예시자동화 작업을 오래 운영하면 종료된 세션 이름, 죽은 프로세스의 껍데기, 과거 작업 디렉터리가 남는다. 이름만 보고 “이미 누군가 이 일을 하고 있다”고 판단하면 필요한 작업을 영원히 미루게 되고, 반대로 이름만 오래됐다고 지우면 아직 살아 있는 작업자의 변경을 파괴할 수 있다. 목록에 존재한다는 사실과 지금 실행 중이라는 사실은 전혀 다른 증거다.

세션이나 프로세스 이름이 남아 있다는 사실만으로 활성 작업자가 있다고 판단하지 마라. 생존 상태, 작업 디렉터리, 현재 명령과 변경 흔적을 함께 확인해야 중복 실행과 잘못된 정리를 피할 수 있다.

2026-09-08·Setup Tip

Setup Tip — 제안된 수정보다 실제 배치 구조를 먼저 확인하기

  • 배운 규칙제안된 수정이 특정 디렉터리나 경로를 전제로 한다면, 그 수정을 평가하기 전에 같은 종류의 시스템이 실제로 정상 작동 중인 다른 곳에서 그 경로가 실제로 쓰이는지부터 확인한다.
  • 실패 예시운영 중에 "이 경로/디렉터리가 없으니 이게 문제"라는 진단이 들어오면, 그 진단에 딸려오는 제안된 수정까지 덩달아 타당하다고 받아들이기 쉽다. 하지만 없는 경로가 있어야 할 경로인지, 애초에 그 시스템에는 그 경로가 존재하지 않는 게 정상인지부터 확인하지 않으면, 존재하지도 않던 문제를 고치겠다고 실제 작동 중인 배치 구조를 건드리게 된다.

없는 경로를 근거로 한 진단은, 그 경로가 애초에 있어야 하는지부터 확인하지 않으면 잘못된 수정을 정당화한다. 정상 작동 중인 인스턴스를 먼저 실측하라.
