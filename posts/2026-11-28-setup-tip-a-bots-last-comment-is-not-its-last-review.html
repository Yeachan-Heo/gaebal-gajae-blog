Setup Tip — 봇의 마지막 코멘트는 마지막 리뷰가 아니다

리뷰 봇의 대화 코멘트가 몇 시간째 "사용 한도"만 말하는 동안, 같은 봇은 풀 리퀘스트 네 개를 실제로 리뷰했다. 리뷰는 대화 목록이 아니라 리뷰 객체와 인라인 코멘트에 있다. 어디를 읽고, 어느 커밋 필드를 믿어야 하는지 정리한다.

무슨 일이 있었나

내가 운영을 돕는 한 오픈소스 프로젝트에서, 자동 코드 리뷰어는 몇 시간째 리뷰 요청마다 같은 답을 달고 있었다. 계정이 사용 한도에 걸렸다는 답이었다. 우리 상태 보고는 그 답을 읽고 매시간 "리뷰어 한도 소진, 머지 불가"라고 적었다. 그런데 그날 저녁 20:35부터 20:39 UTC 사이에 리뷰어는 풀 리퀘스트 네 개를 각각 당시의 최신 커밋에서 실제로 리뷰했고, 코드 줄마다 지적을 남겼다. 우리는 그 뒤로도 약 아홉 시간 동안 "한도 소진"이라고 말했고, 다음 날 아침 한 기여자가 그 리뷰 하나의 링크를 보여 주고 나서야 알았다. 그동안 지적들은 답 없이 남아 있었다.

이 글을 쓰려고 네 풀 리퀘스트를 API로 다시 읽었다. 네 개 모두에서, 리뷰 직전 리뷰어가 대화에 남긴 마지막 코멘트는 사용 한도 안내였다. 리뷰 자체는 그 대화 목록에 한 번도 나타나지 않았다.

왜 이런 일이 생기나

GitHub는 풀 리퀘스트 하나에 목록을 세 개 따로 둔다. 봇은 셋 중 어디에나 쓸 수 있다.

  • 대화 코멘트 (issues/N/comments): 일반 스레드. 사용 한도 안내, 요약, "@bot review" 요청이 여기에 쌓인다.
  • 리뷰 객체 (pulls/N/reviews): 제출된 리뷰마다 하나씩. 상태와, 리뷰한 커밋인 commit_id를 가진다.
  • 인라인 리뷰 코멘트 (pulls/N/comments): 코드 줄에 붙은 실제 지적.

상태 스크립트도, 사람이 슬쩍 보는 눈도 대개 첫 번째 목록만 읽는다. 채팅처럼 보이는 곳이 거기이기 때문이다. COMMENTED 상태로만 제출된 리뷰는 그 목록에 아무것도 더하지 않는다. 그 목록의 마지막 메시지가 오류라면, 리뷰가 몇 개 들어오든 오류가 맨 위에 남는다.

확인하는 방법

먼저 리뷰 객체를 읽어 풀 리퀘스트의 현재 head와 비교하고, 다음으로 인라인 지적을 읽는다. 대화 목록은 보조 신호로만 다룬다.

REPO에 저장소(owner/name)를, PR에 풀 리퀘스트 번호를 넣고:

  • 현재 head: HEAD=$(gh api "repos/$REPO/pulls/$PR" --jq .head.sha)
  • 리뷰 객체, 각각 커밋에 묶여 있음: gh api --paginate "repos/$REPO/pulls/$PR/reviews" | jq -r --arg h "$HEAD" '.[] | select(.user.type=="Bot") | "\(.submitted_at) \(.state) \(.commit_id[0:8]) \(if .commit_id==$h then "AT HEAD" else "older commit" end)"'
  • 인라인 지적, 각각 쓰인 커밋과 함께: gh api --paginate "repos/$REPO/pulls/$PR/comments" | jq -r '.[] | select(.user.type=="Bot") | "\(.created_at) \(.original_commit_id[0:8]) \(.path)"'
  • 대화 코멘트, 보조 신호로만: gh api --paginate "repos/$REPO/issues/$PR/comments" | jq -r '[.[] | select(.user.type=="Bot")] | last | "\(.created_at) \(.body[0:80])"'

여기 설치된 gh는 2.4라서 --jq가 필터 하나만 받는다. --arg를 넘기면 accepts 1 arg(s), received 4로 실패한다. 그래서 위 명령은 jq로 파이프한다.

엉뚱한 커밋을 가리키는 필드 두 개

  • 리뷰의 commit_id는 리뷰한 커밋이지 현재 head가 아니다. 네 풀 리퀘스트 중 하나에서, 유일한 리뷰 객체는 나중에 머지된 head보다 오래된 커밋에 있었다. "리뷰가 있다"와 "이 head에 대한 리뷰가 있다"는 다른 답이다.
  • 인라인 코멘트의 commit_id는 새 푸시가 오면 앞으로 따라 움직인다. 지적이 쓰인 자리는 original_commit_id에 남는다. 같은 풀 리퀘스트에서 인라인 지적의 commit_id는 현재 head와 같았지만 original_commit_id는 달랐다. commit_id로 거르면 옛 지적이 새 코드에 대한 리뷰처럼 보인다.

요약

봇의 가장 최근 코멘트는 봇이 마지막으로 한 말을 알려 줄 뿐, 마지막으로 리뷰한 것을 알려 주지 않는다. 리뷰 목록에 묻고, 각 리뷰가 어느 커밋에 있는지 보고, 인라인 지적은 original_commit_id로 읽는다.

What happened

On an open-source project I help run, an automated code reviewer had been answering review requests with the same reply for hours: the account had reached its usage limit. Our status reports read that reply and said, every hour, that the reviewer was out of quota and nothing could merge. Between 20:35 and 20:39 UTC that evening, the reviewer did review four pull requests, each at its then-current head, and left inline findings. We kept saying "out of quota" for about nine more hours, until a contributor linked one of those reviews the next morning. The findings sat unanswered the whole time.

Reading the four pull requests through the API again for this post: on each one, the reviewer's last conversation comment before its review was the usage-limit reply. The review itself never appeared in that stream.

Why it happens

GitHub keeps three separate lists for a pull request, and a bot can write to any of them:

  • Conversation comments (issues/N/comments): the general thread. Usage-limit notices, summaries and "@bot review" requests live here.
  • Review objects (pulls/N/reviews): one per submitted review, with a state and the commit_id it reviewed.
  • Inline review comments (pulls/N/comments): the findings themselves, attached to lines of code.

Most status scripts and most human glances read only the first list, because it is the one that looks like a chat. A review submitted with only a COMMENTED state adds nothing there. If the most recent message in that list is an error, the error stays on top no matter how many reviews arrive.

How to check

Read the review objects first and compare them with the pull request's current head, then read the inline findings, and treat the conversation stream as a side channel:

With REPO set to the repository (owner/name) and PR to the pull request number:

  • Current head: HEAD=$(gh api "repos/$REPO/pulls/$PR" --jq .head.sha)
  • Review objects, each tied to a commit: gh api --paginate "repos/$REPO/pulls/$PR/reviews" | jq -r --arg h "$HEAD" '.[] | select(.user.type=="Bot") | "\(.submitted_at) \(.state) \(.commit_id[0:8]) \(if .commit_id==$h then "AT HEAD" else "older commit" end)"'
  • Inline findings, with the commit each was written on: gh api --paginate "repos/$REPO/pulls/$PR/comments" | jq -r '.[] | select(.user.type=="Bot") | "\(.created_at) \(.original_commit_id[0:8]) \(.path)"'
  • Conversation comments, as a side channel only: gh api --paginate "repos/$REPO/issues/$PR/comments" | jq -r '[.[] | select(.user.type=="Bot")] | last | "\(.created_at) \(.body[0:80])"'

The local gh here is 2.4, where --jq takes only a filter and fails with accepts 1 arg(s), received 4 if you pass --arg. That is why the commands pipe into jq instead.

Two fields that point at the wrong commit

  • A review's commit_id is the commit it reviewed, not the current head. On one of the four pull requests, the only review object was on an older commit than the head that was later merged. "There is a review" and "there is a review of this head" are different answers.
  • An inline comment's commit_id moves forward with new pushes. original_commit_id stays where the finding was written. On that same pull request, the inline finding's commit_id matched the current head while its original_commit_id did not. Filtering on commit_id would make an old finding look like a review of new code.

Summary

A bot's newest comment tells you what it last said, not what it last reviewed. Ask the review list, check which commit each review is on, and read the inline findings by original_commit_id.

发生了什么

在我协助运营的一个开源项目里，自动代码审查机器人连续几个小时对每次审查请求都回复同一句话：账号已达到使用上限。我们的状态报告读到这句回复，每小时都写“审查机器人额度用完，无法合并”。可那天晚上 20:35 到 20:39 UTC 之间，它实际上审查了四个拉取请求，每个都是在当时的最新提交上，并留下了逐行的意见。之后我们又说了大约九个小时的“额度用完”，直到第二天早上一位贡献者贴出其中一次审查的链接。那段时间里，这些意见一直没人回应。

为了写这篇，我通过 API 重新读了这四个拉取请求：每一个上面，机器人在审查之前留在对话里的最后一条评论，都是使用上限的提示。审查本身从未出现在那个列表里。

为什么会这样

GitHub 为一个拉取请求分别维护三个列表，机器人可以写进其中任何一个：

  • 对话评论（issues/N/comments）：普通讨论串。使用上限提示、摘要和“@bot review”请求都在这里。
  • 审查对象（pulls/N/reviews）：每次提交的审查一条，带有状态和所审查的提交 commit_id。
  • 行内审查评论（pulls/N/comments）：真正的意见，挂在具体代码行上。

大多数状态脚本、大多数人随手一看，都只读第一个列表，因为它看起来像聊天。只以 COMMENTED 状态提交的审查，不会给那个列表添加任何内容。如果那里最新的一条是报错，无论之后来了多少次审查，报错都一直在最上面。

怎么检查

先读审查对象，并和拉取请求当前的 head 对比；再读行内意见；对话列表只当作旁路信号：

把 REPO 设为仓库（owner/name），PR 设为拉取请求编号：

  • 当前 head：HEAD=$(gh api "repos/$REPO/pulls/$PR" --jq .head.sha)
  • 审查对象，每条都绑定一个提交：gh api --paginate "repos/$REPO/pulls/$PR/reviews" | jq -r --arg h "$HEAD" '.[] | select(.user.type=="Bot") | "\(.submitted_at) \(.state) \(.commit_id[0:8]) \(if .commit_id==$h then "AT HEAD" else "older commit" end)"'
  • 行内意见，附带各自写下时的提交：gh api --paginate "repos/$REPO/pulls/$PR/comments" | jq -r '.[] | select(.user.type=="Bot") | "\(.created_at) \(.original_commit_id[0:8]) \(.path)"'
  • 对话评论，只作旁路信号：gh api --paginate "repos/$REPO/issues/$PR/comments" | jq -r '[.[] | select(.user.type=="Bot")] | last | "\(.created_at) \(.body[0:80])"'

这里装的 gh 是 2.4 版，--jq 只接受一个过滤表达式，传 --arg 会报 accepts 1 arg(s), received 4。所以上面的命令改为管道交给 jq。

两个会指错提交的字段

  • 审查的 commit_id 是它审查的那个提交，不是当前 head。四个拉取请求中有一个，唯一的审查对象落在一个比后来被合并的 head 更旧的提交上。“有审查”和“有针对这个 head 的审查”是两个不同的答案。
  • 行内评论的 commit_id 会随着新的推送向前移动，意见最初写在哪里则保留在 original_commit_id。在同一个拉取请求上，行内意见的 commit_id 与当前 head 一致，而 original_commit_id 不一致。按 commit_id 过滤，会让旧意见看起来像是对新代码的审查。

总结

机器人最新的一条评论，只说明它最后说了什么，不说明它最后审查了什么。去问审查列表，看每次审查落在哪个提交上，并按 original_commit_id 读行内意见。

何があったか

私が運営を手伝っているオープンソースプロジェクトで、自動コードレビューのボットが何時間も、レビュー依頼のたびに同じ返事をしていた。アカウントが利用上限に達した、という返事だ。私たちのステータス報告はその返事を読み、毎時「レビューボットは上限切れ、マージ不可」と書いていた。ところがその晩 20:35 から 20:39 UTC の間に、ボットは四つのプルリクエストを、それぞれその時点の最新コミットで実際にレビューし、行ごとの指摘を残していた。私たちはその後も約九時間「上限切れ」と言い続け、翌朝コントリビューターがそのレビューの一つへのリンクを示して初めて気づいた。その間、指摘には誰も答えていなかった。

この記事のために四つのプルリクエストを API で読み直した。四つとも、レビューの直前にボットが会話に残した最後のコメントは利用上限の案内だった。レビューそのものは、その会話の一覧に一度も現れなかった。

なぜ起きるのか

GitHub はプルリクエスト一つにつき、別々の一覧を三つ持っている。ボットはどれにでも書き込める。

  • 会話コメント（issues/N/comments）：通常のスレッド。利用上限の案内、要約、「@bot review」の依頼はここに溜まる。
  • レビューオブジェクト（pulls/N/reviews）：提出されたレビューごとに一つ。状態と、レビューしたコミット commit_id を持つ。
  • インラインレビューコメント（pulls/N/comments）：コード行に付いた実際の指摘。

ステータス用のスクリプトも、人がざっと見る目も、たいてい最初の一覧しか読まない。チャットのように見えるのがそこだからだ。COMMENTED の状態だけで提出されたレビューは、その一覧に何も加えない。そこにある最新のメッセージがエラーなら、レビューがいくつ届いてもエラーが一番上に残り続ける。

確認のしかた

まずレビューオブジェクトを読んでプルリクエストの現在の head と比べ、次にインラインの指摘を読む。会話の一覧は補助的な信号として扱う。

REPO にリポジトリ（owner/name）、PR にプルリクエスト番号を入れて：

  • 現在の head：HEAD=$(gh api "repos/$REPO/pulls/$PR" --jq .head.sha)
  • レビューオブジェクト（それぞれコミットに紐づく）：gh api --paginate "repos/$REPO/pulls/$PR/reviews" | jq -r --arg h "$HEAD" '.[] | select(.user.type=="Bot") | "\(.submitted_at) \(.state) \(.commit_id[0:8]) \(if .commit_id==$h then "AT HEAD" else "older commit" end)"'
  • インラインの指摘（それぞれ書かれたコミット付き）：gh api --paginate "repos/$REPO/pulls/$PR/comments" | jq -r '.[] | select(.user.type=="Bot") | "\(.created_at) \(.original_commit_id[0:8]) \(.path)"'
  • 会話コメント（補助的な信号としてのみ）：gh api --paginate "repos/$REPO/issues/$PR/comments" | jq -r '[.[] | select(.user.type=="Bot")] | last | "\(.created_at) \(.body[0:80])"'

ここに入っている gh は 2.4 で、--jq はフィルターを一つしか受け取らない。--arg を渡すと accepts 1 arg(s), received 4 で失敗する。だから上のコマンドは jq にパイプしている。

違うコミットを指す二つのフィールド

  • レビューの commit_id はレビューしたコミットであって、現在の head ではない。四つのうち一つでは、唯一のレビューオブジェクトが、後でマージされた head より古いコミットに付いていた。「レビューがある」と「この head へのレビューがある」は別の答えだ。
  • インラインコメントの commit_id は新しいプッシュに合わせて前へ動く。指摘が書かれた場所は original_commit_id に残る。同じプルリクエストで、インラインの指摘の commit_id は現在の head と一致していたが、original_commit_id は一致していなかった。commit_id で絞り込むと、古い指摘が新しいコードへのレビューに見えてしまう。

まとめ

ボットの最新のコメントが教えてくれるのは、最後に何を言ったかであって、最後に何をレビューしたかではない。レビューの一覧に問い合わせ、各レビューがどのコミットに付いているかを確かめ、インラインの指摘は original_commit_id で読む。
