Setup Tip — 성공한 푸시가 풀 리퀘스트를 비껴갈 수 있다

자동화 작업 세 개가 풀 리퀘스트에 수정을 푸시했다고 보고했지만, 풀 리퀘스트는 한 번도 바뀌지 않았다. 각자 새 브랜치에 푸시했고, git은 매번 성공을 알렸다. 풀 리퀘스트의 브랜치 이름으로 푸시하고, `[new branch]`를 오류로 다루고, 푸시 후에는 풀 리퀘스트의 헤드 커밋을 내 커밋과 비교한다.

무슨 일이 있었나

어제 한 오픈소스 프로젝트의 열린 풀 리퀘스트 하나에서 테스트를 고치는 일을 자동화 작업 세 개가 차례로 맡았다. 셋 다 수정을 푸시했다고 보고했다. 그때마다 풀 리퀘스트는 바뀌지 않았다. 저장소 API에서 그 풀 리퀘스트의 커밋 목록을 보면 12:37 UTC에 커밋 하나, 그다음은 16:27 UTC로 찍힌 커밋인데, 이것도 나중에 따로 풀 리퀘스트 브랜치에 푸시되고 나서야 들어갔다. 작업들이 만든 커밋 중 하나는 아직 남아 있다. 15:50 UTC에 커밋되었고, 당시 풀 리퀘스트 헤드 바로 위에 커밋 하나로 올라가 있으며, 풀 리퀘스트에는 한 번도 들어가지 않았다. 작업들은 각자 새 브랜치에 푸시했고, 푸시는 매번 성공했다.

푸시 성공이 풀 리퀘스트에 대해 말해 주지 않는 이유

풀 리퀘스트는 원격의 브랜치 하나를 따라간다. 푸시는 내가 보낸 ref를 원격이 받아들이면 성공한다. 그 ref가 무엇이든 상관없다. 푸시한 브랜치 이름이 다르면 git은 그 브랜치를 새로 만들고, 성공을 알리고, 0으로 끝난다. 풀 리퀘스트는 제자리에 있다.

재현

git 2.34.1에서 bare 저장소를 만들고, 풀 리퀘스트 역할로 feature 브랜치를 푸시한 뒤, 새로 체크아웃하는 작업처럼 다시 클론했다.

  • git switch -c work/lane-1 origin/feature → git push -u origin HEAD

푸시는 * [new branch] HEAD -> work/lane-1을 출력하고 0으로 끝났다. 이어서 git ls-remote origin을 보니 feature는 이전 커밋에 그대로 있고, 수정은 새로 생긴 work/lane-1에 들어 있었다. 대상 이름에 오타를 낸 HEAD:feature-typo 푸시도, 로컬 HEAD가 브랜치 위에 있으면 새 브랜치를 만들고 0으로 끝났다. HEAD가 분리된 상태일 때만 git이 The destination you provided is not a full refname으로 거부했다.

기본 설정이 막아 줄 수도 있다, 그대로 두면

push.default를 설정하지 않은 상태(기본값 simple)에서 git switch -c work/lane-2 --track origin/feature으로 만든 브랜치는 인자 없는 git push를 The upstream branch of your current branch does not match the name of your current branch로 거부했다. 이 거부는 쓸모가 있다. 그런데 이를 넘기려고 -u origin HEAD를 붙이는 순간 사라지고, 바로 그게 새 브랜치를 만든다.

풀 리퀘스트의 브랜치 이름으로 푸시한다

풀 리퀘스트에 헤드가 어디인지 물은 다음, 그곳에 명시적으로 푸시한다.

  • gh api "repos/{owner}/{repo}/pulls/$PR" --jq '.head.ref, .head.sha'
  • git push origin HEAD:"$BRANCH"

두 번째 명령은 기존 브랜치를 옮기면 old..new HEAD -> feature를 출력한다. [new branch]가 나오면 이름이 틀린 것이다. 스크립트에서는 git push --porcelain가 ref마다 한 줄씩, 같은 [new branch] 표시와 함께 출력하므로 작업이 이를 보고 멈출 수 있다.

풀 리퀘스트가 움직였는지 확인한다

증거는 푸시 출력이 아니라 풀 리퀘스트다. 푸시한 뒤 풀 리퀘스트의 헤드를 내 커밋과 비교한다.

  • [ "$(gh api "repos/{owner}/{repo}/pulls/$PR" --jq .head.sha)" = "$(git rev-parse HEAD)" ] && echo "PR updated" || echo "PR NOT updated"

재현에서 작업의 푸시는 성공을 출력했고, 이 확인은 PR NOT updated: PR head 8764f2c, local 674b017을 출력했다. git push origin HEAD:feature 뒤에는 PR updated가 나왔다. API 없이 git ls-remote origin "refs/heads/$BRANCH"로도 같은 답을 얻는다. 내가 쓴 gh CLI 2.4에서는 gh pr view --json에 headRefOid 필드가 없어서, 위의 API 호출이 어디서나 통하는 방법이다.

자동화 작업에 맡길 때

작업에게 풀 리퀘스트의 브랜치 이름과, 그 위에 쌓아야 할 헤드 커밋을 함께 준다. 마지막에 위의 비교를 하게 하고, "푸시함"이 아니라 풀 리퀘스트의 새 헤드 커밋을 보고하게 한다. 그 커밋이 없는 보고는 어떤 브랜치에 대한 보고일 뿐, 풀 리퀘스트에 대한 보고가 아니다.

정리

"푸시했다"는 원격이 ref 하나를 받았다는 뜻이다. 어느 ref인지는 말해 주지 않는다. 풀 리퀘스트의 브랜치 이름으로 푸시하고, [new branch]를 오류로 다루고, 푸시 후에는 풀 리퀘스트의 헤드 커밋을 보고한다.

What happened

Yesterday three automated tasks in a row were asked to fix the tests on one open pull request in an open-source project. Each one reported that it had pushed its fix. Each time, the pull request did not change. The pull request's commit list on the repository API shows one commit at 12:37 UTC and the next dated 16:27 UTC, which reached the pull request only because it was later pushed to the pull request's branch separately. One of the tasks' commits still exists: it was committed at 15:50 UTC, sits exactly one commit on top of the pull request's head at the time, and was never part of the pull request. The tasks had pushed to new branches of their own, and every push succeeded.

Why a successful push says nothing about the pull request

A pull request follows one branch on the remote. A push succeeds when the remote accepts the ref you sent, whichever ref that is. If the branch you push has a different name, git creates it, reports success and exits 0, and the pull request stays where it was.

Reproducing it

With git 2.34.1 I made a bare repository, pushed a feature branch to stand in for the pull request, and cloned it again the way a task with a fresh checkout would.

  • git switch -c work/lane-1 origin/feature → git push -u origin HEAD

The push printed * [new branch] HEAD -> work/lane-1 and exited 0. git ls-remote origin then showed feature still on the old commit and a new work/lane-1 holding the fix. Pushing HEAD:feature-typo, with a typo in the target name, also created a new branch and exited 0, as long as the local HEAD was on a branch. Only with a detached HEAD did git refuse with The destination you provided is not a full refname.

The default can catch it, if you let it

With push.default left unset (the default, simple), a branch made with git switch -c work/lane-2 --track origin/feature refused a bare git push with The upstream branch of your current branch does not match the name of your current branch. That refusal is useful. It disappears the moment someone adds -u origin HEAD to get past it, which is exactly what makes the new branch.

Push to the pull request's branch by name

Ask the pull request where its head is, then push there explicitly.

  • gh api "repos/{owner}/{repo}/pulls/$PR" --jq '.head.ref, .head.sha'
  • git push origin HEAD:"$BRANCH"

The second command prints old..new HEAD -> feature when it moves the existing branch. If it prints [new branch], the name was wrong. In scripts, git push --porcelain prints one line per ref with the same [new branch] flag, so a job can stop on it.

Confirm the pull request moved

The proof is the pull request, not the push output. After pushing, compare the pull request's head with your commit.

  • [ "$(gh api "repos/{owner}/{repo}/pulls/$PR" --jq .head.sha)" = "$(git rev-parse HEAD)" ] && echo "PR updated" || echo "PR NOT updated"

In the reproduction, the task's push printed success and this check printed PR NOT updated: PR head 8764f2c, local 674b017. After git push origin HEAD:feature it printed PR updated. git ls-remote origin "refs/heads/$BRANCH" gives the same answer without the API. With the gh CLI 2.4 I had, gh pr view --json has no headRefOid field, so the API call above is the portable form.

For automated tasks

Give the task the pull request's branch name and the head commit it should build on. Have it end with the comparison above and report the pull request's new head commit, not "pushed". A report without that commit is a report about some branch, not about the pull request.

Summary

"Pushed" means the remote took a ref. It does not say which one. Push to the pull request's branch by name, treat [new branch] as an error, and report the pull request's head commit after the push.

发生了什么

昨天，一个开源项目里某个打开着的拉取请求需要修测试，三个自动化任务先后接手。三个都报告说已经推送了修复。每一次，拉取请求都没有变化。从仓库 API 看这个拉取请求的提交列表：12:37 UTC 有一个提交，下一个提交的时间是 16:27 UTC，它也是后来被另外推送到拉取请求的分支上才进去的。任务做出的提交中有一个至今还在：它提交于 15:50 UTC，正好在当时拉取请求头提交之上多一个提交，却从未进入拉取请求。这些任务各自推送到了自己新建的分支，而且每次推送都成功了。

推送成功为什么说明不了拉取请求

拉取请求跟随的是远端的某一个分支。只要远端接受了你发送的 ref，推送就算成功，不管那是哪个 ref。如果你推送的分支名字不同，git 会新建它、报告成功、以 0 退出，而拉取请求原地不动。

复现

我用 git 2.34.1 建了一个 bare 仓库，推送一个 feature 分支来代表拉取请求，然后像一个全新检出的任务那样重新克隆。

  • git switch -c work/lane-1 origin/feature → git push -u origin HEAD

推送输出了 * [new branch] HEAD -> work/lane-1 并以 0 退出。接着 git ls-remote origin 显示 feature 还停在旧提交，修复落在新出现的 work/lane-1 上。目标名打错的 HEAD:feature-typo 推送，只要本地 HEAD 在某个分支上，同样新建分支并以 0 退出。只有在 HEAD 分离时，git 才会以 The destination you provided is not a full refname 拒绝。

默认设置能拦住它，前提是别绕过

在没有设置 push.default（默认值 simple）时，用 git switch -c work/lane-2 --track origin/feature 建出的分支，执行不带参数的 git push 会被拒绝：The upstream branch of your current branch does not match the name of your current branch。这个拒绝是有用的。可一旦有人为了绕过它加上 -u origin HEAD，它就消失了，而这恰恰就是新建分支的那一步。

按拉取请求的分支名推送

先问拉取请求它的头在哪里，再明确地推送到那里。

  • gh api "repos/{owner}/{repo}/pulls/$PR" --jq '.head.ref, .head.sha'
  • git push origin HEAD:"$BRANCH"

第二条命令移动已有分支时会输出 old..new HEAD -> feature。如果输出的是 [new branch]，说明名字错了。在脚本里，git push --porcelain 每个 ref 输出一行，带着同样的 [new branch] 标记，任务可以据此停下。

确认拉取请求真的动了

证据是拉取请求，而不是推送的输出。推送之后，把拉取请求的头提交和你的提交比一比。

  • [ "$(gh api "repos/{owner}/{repo}/pulls/$PR" --jq .head.sha)" = "$(git rev-parse HEAD)" ] && echo "PR updated" || echo "PR NOT updated"

在复现中，任务的推送显示成功，而这个检查输出 PR NOT updated: PR head 8764f2c, local 674b017。执行 git push origin HEAD:feature 之后，输出变成 PR updated。不用 API 的话，git ls-remote origin "refs/heads/$BRANCH" 也能给出同样的答案。我用的 gh CLI 2.4 里，gh pr view --json 没有 headRefOid 字段，所以上面的 API 调用是通用写法。

交给自动化任务时

把拉取请求的分支名和它应当基于的头提交一起交给任务。让它最后做上面的比对，并报告拉取请求新的头提交，而不是“已推送”。没有这个提交的报告，说的只是某个分支，不是拉取请求。

总结

“已推送”的意思是远端收下了一个 ref，并没有说是哪一个。按拉取请求的分支名推送，把 [new branch] 当作错误，推送之后报告拉取请求的头提交。

何があったか

昨日、あるオープンソースプロジェクトの開いているプルリクエスト一つで、テストを直す作業を自動化タスク三つが順に引き受けた。三つとも修正をプッシュしたと報告した。そのたびに、プルリクエストは変わらなかった。リポジトリ API でそのプルリクエストのコミット一覧を見ると、12:37 UTC にコミットが一つ、次は 16:27 UTC 付けのコミットで、これも後から別にプルリクエストのブランチへプッシュされて初めて入った。タスクが作ったコミットの一つは今も残っている。15:50 UTC にコミットされ、当時のプルリクエストのヘッドのちょうど一つ上に載っていて、一度もプルリクエストに入らなかった。タスクはそれぞれ自分で新しいブランチにプッシュしており、プッシュは毎回成功していた。

プッシュの成功がプルリクエストについて何も語らない理由

プルリクエストはリモートのブランチ一つを追いかける。プッシュは、送った ref をリモートが受け取れば成功する。それがどの ref でも関係ない。プッシュしたブランチの名前が違えば、git はそれを新しく作り、成功を伝え、0 で終わる。プルリクエストはその場から動かない。

再現

git 2.34.1 で bare リポジトリを作り、プルリクエスト役として feature ブランチをプッシュし、新しくチェックアウトするタスクのように改めてクローンした。

  • git switch -c work/lane-1 origin/feature → git push -u origin HEAD

プッシュは * [new branch] HEAD -> work/lane-1 と表示して 0 で終わった。続けて git ls-remote origin を見ると、feature は古いコミットのままで、修正は新しくできた work/lane-1 に入っていた。宛先名を打ち間違えた HEAD:feature-typo へのプッシュも、ローカルの HEAD がブランチ上にあれば新しいブランチを作って 0 で終わった。HEAD が切り離された状態のときだけ、git は The destination you provided is not a full refname で拒否した。

既定の設定が止めてくれる、そのままにしておけば

push.default を設定していない状態（既定値 simple）で git switch -c work/lane-2 --track origin/feature で作ったブランチは、引数なしの git push を The upstream branch of your current branch does not match the name of your current branch で拒否した。この拒否は役に立つ。ところが、それを避けようと -u origin HEAD を付けた瞬間に消え、まさにそれが新しいブランチを作る。

プルリクエストのブランチ名でプッシュする

プルリクエストにヘッドがどこかを尋ね、そこへ明示的にプッシュする。

  • gh api "repos/{owner}/{repo}/pulls/$PR" --jq '.head.ref, .head.sha'
  • git push origin HEAD:"$BRANCH"

二つ目のコマンドは、既存のブランチを動かしたときは old..new HEAD -> feature と表示する。[new branch] と出たら名前が間違っている。スクリプトでは git push --porcelain が ref ごとに一行、同じ [new branch] の印付きで出力するので、タスクはそれを見て止まれる。

プルリクエストが動いたことを確かめる

証拠はプッシュの出力ではなく、プルリクエストだ。プッシュした後、プルリクエストのヘッドを自分のコミットと比べる。

  • [ "$(gh api "repos/{owner}/{repo}/pulls/$PR" --jq .head.sha)" = "$(git rev-parse HEAD)" ] && echo "PR updated" || echo "PR NOT updated"

再現では、タスクのプッシュは成功を表示し、この確認は PR NOT updated: PR head 8764f2c, local 674b017 と出した。git push origin HEAD:feature の後は PR updated になった。API を使わなくても git ls-remote origin "refs/heads/$BRANCH" で同じ答えが得られる。私の使った gh CLI 2.4 では gh pr view --json に headRefOid フィールドがないので、上の API 呼び出しがどこでも通る書き方だ。

自動化タスクに任せるとき

タスクにはプルリクエストのブランチ名と、その上に積むべきヘッドコミットを一緒に渡す。最後に上の比較をさせ、「プッシュした」ではなくプルリクエストの新しいヘッドコミットを報告させる。そのコミットがない報告は、どこかのブランチについての報告であって、プルリクエストについての報告ではない。

まとめ

「プッシュした」は、リモートが ref を一つ受け取ったという意味だ。どの ref かは言っていない。プルリクエストのブランチ名でプッシュし、[new branch] をエラーとして扱い、プッシュ後はプルリクエストのヘッドコミットを報告する。

Setup Tip — cancel-in-progress: false여도 커밋은 건너뛰어진다

  • 배운 규칙어제 개발 브랜치에 풀 리퀘스트 세 개를 8초 안에 머지했다. CI 설정은 cancel-in-progress: false였으니 커밋마다 테스트가 돌 거라고 생각했다. 실제로는 앞의 두 커밋 실행이 잡 하나 없이 몇 초 만에 취소되었고, 테스트된 것은 마지막 커밋뿐이었다. GitHub Actions의 concurrency 그룹은 실행 중인 것 하나와 대기 중인 것 하나만 둔다. 대기 중이던 실행은 더 새 실행이 들어오면 취소된다.
